## 2. NFC support: physical capability and transport constraint

**Official product scope (supplementary, not a pinned corpus source):** Nintendo documents an NFC reader/writer touchpoint on the Switch Pro Controller and specifically states that NFC does not operate while the controller is using **Pro Controller Wired Communication**. Nintendo's support diagram and wired-connection guidance are cited below. Consequently, an emulated USB/wired Switch Pro that lacks NFC is **not**, by that fact alone, violating expected wired behavior. NFC should not be invented on the current `linux.uhid.usb` realization to satisfy a feature checklist. The interesting fidelity question is the distinct wireless/native interface and whether a real compatible consumer initiates MCU/NFC transactions.

**Pinned protocol context:** Existing research source records `swpro-dekunukem-bluetooth-hid-notes` and `swpro-dekunukem-bluetooth-hid-subcommands-notes` (both revision `b354f21ae81f7b0d1d060b2b61e66ad0d9bc1756`) describe controller-family output report `0x11`, input report `0x31`, MCU reset/configuration/state subcommands `0x20`–`0x22`, and the required report mode/polling distinction. This is not a measured Pro-specific NFC state machine; the cited documents discuss the Nintendo Switch controller family and may cover Joy-Con paths not available on the Pro. The `joycon-b-nfc-state-machine` claim is specifically a **Joy-Con Right consumer** claim and must not be promoted to Pro device evidence.

**Current virtualgamepad comparison:** `crates/gr-curated-controllers/src/switch_pro.rs` emits full input report `0x30` (around lines 713–714) and only enables streaming on report-mode request `0x03` with argument `0x30` (lines 796–800). The subcommand `0x21` returns a limited `0xA0` ACK (line 804); this **is not an NFC implementation or validated hardware reply**. `switch_pro/protocol.rs` (lines 54–71) processes output report `0x01`, rumble-only `0x10`, and USB command `0x80`, not a separate MCU data output `0x11`. There is no per-controller NFC/MCU lifecycle state or input `0x31` producer in the reviewed realization. Available production targets are USB-based or generic evdev; no physical Bluetooth realization has been accepted (#164).

**Engineering impact:** Declare NFC as a currently unsupported **wireless/native feature**, instead of claiming that ordinary USB controls must support it. If a future Switch Pro Bluetooth realization or console-facing emulation is pursued, inventory the NFC transaction shape against Pro-specific evidence and add typed MCU/NFC lifecycle support only after the data path and consumer are known. Do not copy a Joy-Con NFC state machine unchanged. Reuse common Nintendo protocol code only for independently evidenced identical behavior. There is no request here to implement NFC, modify a virtualgamepad issue body, or start a Bluetooth provider.

**Not established:** real Pro MCU command/reply bytes; exact wireless packet framing and connection prerequisites; actual host NFC consumer workflow; whether non-console Linux consumers access the feature; NFC tag operations, error sequences and timing. No tag contents, calibration data or sensitive identifiers are available or authorized for publication.

**Proposed physical gate (not run):** If the owner later has a retail Pro Controller and supported host, compare a minimal non-content-bearing wireless NFC initiation and cancellation with virtual behavior, noting only sanitized report types, command IDs, ACK/retry outcomes and state transitions. Keep any legitimate tag contents and per-device identities outside the public corpus. Confirm Nintendo's wired NFC restriction independently, and do not mistake a wired negative test for a failed NFC implementation. Capture work requires owner permission; no hardware test is implied.

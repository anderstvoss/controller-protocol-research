# Steam Controller 2026 modes: follow-up on HIDINPUT, lizard restoration and Steam activation

**Scope:** source-only follow-up to [merged modes research #103](steam-controller-modes.md), [Steam-client detection #102](steam-client-detection.md), [D9 physical report #101](steam-d9-detection-physical-2026-11-04.md), and the [physical 372-byte descriptor #82](steam-s3-physical-descriptor.md). Target remains wired `28de:1302`. No access to Linux, hardware, Steam runtime or local virtualgamepad code. Three distinct additional findings follow; none changes the physical D9 record or proves a retail wired watchdog timeout.

**Evidence labels:** **[K]** pinned Linux host source, **[Puck]** independently published *Puck-path* owner observation, **[Host report]** public issue author's report on an **unrelated generic controller**, **[Inference]** prediction pending D9 test. Do not treat any public user report as a controlled D9 experiment. No GPL code excerpt or identifying USB data is reproduced.

## 1. Firmware mouse/keyboard events are not disabled by a raw-hid client opening

**Source-grounded result.** The physical descriptor for direct wired `1302` has **one USB interface** with *three distinct HID top-level application collections* (mouse `0001:0002`, keyboard `0001:0006`, vendor `ff00:0001`). The mouse and keyboard inputs use **report IDs `0x40` (6 wire bytes)** and **`0x41` (9 wire bytes)**; the native gamepad uses vendor `0x42`. See [#82](steam-s3-physical-descriptor.md) and `steam-s3-1302-report-shapes`.

Linux `hid-steam` has two HID devices for the native controller path, not two separate physical USB interfaces:
1. Its **underlying physical HID** starts with `HID_CONNECT_DEFAULT & ~HID_CONNECT_HIDRAW`, retaining the standard HID input connection.
2. Its **layered client_hdev** starts with `HID_CONNECT_HIDRAW` only. When an application opens that client, `client_opened` rises, and the kernel **synthetic** evdev gamepad and motion nodes unregister asynchronously.
3. On incoming reports, `hid-steam` forwards to `client_hdev` if a client is open. The IBEX-specific raw-event switch handles `0x42`/`0x45` as native gamepad/sensors (skipping kernel synthetic decode if client-opened); it does **not** suppress `0x40`/`0x41` via a special return. The raw callback returns zero.
4. The pinned HID core then normally parses the **original physical HID** report fields and emits HIDINPUT events for input-connected reports. The layered client is HIDRAW-only, so this does **not** create a second keyboard through that client.

Evidence: [`hid-steam.c:1706–1759,1782–1787`](https://github.com/torvalds/linux/blob/cee9395acd8043be0644b25c34bfa86623f2b935/drivers/hid/hid-steam.c#L1706-L1787), [`hid-steam.c:2530–2619`](https://github.com/torvalds/linux/blob/cee9395acd8043be0644b25c34bfa86623f2b935/drivers/hid/hid-steam.c#L2530-L2619), [`hid.h:351–359`](https://github.com/torvalds/linux/blob/cee9395acd8043be0644b25c34bfa86623f2b935/include/linux/hid.h#L351-L359), [`hid-core.c:2043–2118,2173–2180`](https://github.com/torvalds/linux/blob/cee9395acd8043be0644b25c34bfa86623f2b935/drivers/hid/hid-core.c#L2100-L2118).

**Consequence:** `client_opened > 0` removes the kernel's **native gamepad/motion evdev**, **not** the controller firmware's potential lizard keyboard/mouse input. **[Inference]** If the emulator continues to emit `0x40`/`0x41` while Steam also creates desktop mouse/keyboard mappings, double pointer/key input could occur. This is why suppression must be modeled on the *device protocol* and not tied solely to raw-client existence. Conversely, physical wired `1302` actual mapped events still require D9 observation. The source only establishes host routing conditional on reports being emitted and recognized by the HID parser.

**Do not revise the O5 matrix to say “lizard absent on raw open.”** The lizard column is determined by firmware-side `0x81/0x85/0x8e` and `0x87` setting9/71 processing and watchdog behavior, not by the Linux `client_opened` Boolean.

## 2. A measured Puck restoration is not a measured wired watchdog

The pinned independent [CouchTurtle `HID_REPORT_FORMAT.md:113–123`](https://github.com/CouchTurtle/sc2-research/blob/b46d5173501ec6814cb99c5769289ffce72f488d/docs/HID_REPORT_FORMAT.md#L113-L123) reports a **physical Puck path** experiment on **2026-05-19**: after terminating Steam, mouse and keyboard `0x40/0x41` returned *within about eight seconds*; first reports indicated neutral state, and subsequent lizard output was change-triggered. Once Steam was restarted, these reports stopped again. **[Puck]** This supports physical *end-to-end* lizard restoration and the report-ID roles, not direct-wired `1302` timing. The source explicitly identifies a Puck USB slot endpoint; this is not the wired controller's physical interface [CouchTurtle:37–60](https://github.com/CouchTurtle/sc2-research/blob/b46d5173501ec6814cb99c5769289ffce72f488d/docs/HID_REPORT_FORMAT.md#L37-L60).

**Critical confound:** `kill -9` of Steam closes process-owned raw-HID file descriptors. With `hid-steam` bound, final client close schedules `work_connect`, which can **re-register and send `0x85/0x8e` default mapping/settings immediately** [K:1461–1485,1372–1407,1650–1675](https://github.com/torvalds/linux/blob/cee9395acd8043be0644b25c34bfa86623f2b935/drivers/hid/hid-steam.c#L1461-L1485). The published Puck test does not establish kernel binding/version or rule out these host writes. Therefore **an ~8 s observation after Steam exit must not be called the isolated stock firmware watchdog period**. The existing OpenPuck 7-second window is a **receiver emulation choice** [OpenPuck:185–210](https://github.com/safijari/openpuck/blob/29f4d1e8b85c0a7c19e0c8b977a1a56a2c42ea6d/OpenPuck/puck_hid.cpp#L185-L210); sc26re uses a 10-second replacement-firmware timer [sc26re:19–30,308–395](https://github.com/mwdmwd/sc26re/blob/518fa645067f1dd6012f910a4575e487eccc9a5c/app/src/lizard.c#L308-L395); SDL3 refreshes lizard-disable on its *host* update loop every ~3 seconds [SDL3:485–499](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/hidapi/SDL_hidapi_steam_triton.c#L485-L499). They are **not** measured values for the same device/transport/firmware state.

**Kernel-probe interaction:** On its lizard-off path the kernel sends setting9=0 **and** setting71=0 (watchdog disabled by kernel policy) [K:880–905](https://github.com/torvalds/linux/blob/cee9395acd8043be0644b25c34bfa86623f2b935/drivers/hid/hid-steam.c#L880-L905). This makes a naïve “stop refreshing and wait” experiment more complicated than a single timeout; restore via a kernel SET and restore via a firmware timer must be separated. The replacement firmware's key71 behavior illustrates an implementation possibility, **not proven stock logic**.

**Owner test, passive only:** With owner consent, correlate (a) relative time of last lizard-off setting9=0/other output, (b) closing the last raw client, (c) kernel `0x85/0x8e` or setting9/71 writes, and (d) first physical `0x40/0x41` after the transition. If host re-enable writes are observed, record the result **host-restored or confounded**, *not* “firmware watchdog ~N seconds.” A true autonomous timer measurement would require separately reviewed host conditions that avoid restore writes and ensure no active reader sends a heartbeat; **this research issues no raw reports, driver unbind or firmware commands**. Puck observations should be labeled receiver-path, and direct wired observations separately.

## 3. Steam discovery, activation, and translated-device emission are separate gates

There are at least **five independently observable checkpoints** on the Linux host, which can succeed or fail in different combinations:

| Stage | Observable evidence | Who determines it | What it **does not** prove |
| --- | --- | --- | --- |
| **A. HID enumeration** | Physical/virtual HID ID and descriptor, bind, hidraw and input-node inventory | USB/UHID and kernel | Whether SDL or Steam accepts controller |
| **B. SDL/openable raw input** | SDL HIDAPI recognizes and decodes `0x42`; a raw handle exists | SDL + `hid-steam` | Whether Steam has activated the controller |
| **C. Steam discovery** | `controller.txt` discovery / attempted controller index | Steam client | Whether opened, initialized or managed |
| **D. Steam activation** | Successful managed-controller open, stable setting/heartbeat activity and Steam input configuration | Proprietary Steam client | Whether a translated virtual device currently exists |
| **E. Game-visible translated output** | `28de:11ff` kernel virtual gamepad **exists and emits** during a game, or Steam synthetic pointer/keys reach target; game API sees it | Steam Input, desktop/game context, SDL filters or Proton/Wine | Whether **physical** gamepad is simultaneously hidden from every API |

**[Host report, not 1302]** In [ValveSoftware/steam-for-linux #13394 (2026-07-07)](https://github.com/ValveSoftware/steam-for-linux/issues/13394), a user presents logs of a **generic unrelated controller** (`11ff:3331`, not Steam's `28de:11ff`) that reached “Local Device Found” but failed the later managed-open and XInput-slot-reservation steps; normal SDL input still worked outside Steam. This is valuable evidence that the *log stages* must be tracked separately, but it does **not** establish that the same failure condition afflicts the wired 1302 or that a reported udev 259 update caused it. This public issue body is mutable/unpinned testimony, **not** a new pinned source record and **not** a physical validation of D9.

**[Implementation]** Published [Proton `CONTROLLERS.md:81–107`](https://github.com/ValveSoftware/Proton/blob/bc896217ffcd67f892f952b010f898fe7bd0f0a1/docs/CONTROLLERS.md#L81-L107) explains that a mapped controller may reach a Windows game as translated virtual **XInput** *alongside* direct APIs; that differs from native SDL evdev/HIDAPI filtering. SDL3's Linux virtual-pad identity is **`28de:11ff`**, which SDL gamepad APIs ignore by default unless its explicit allow hint is enabled [SDL joystick:3507–3513](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/SDL_joystick.c#L3507-L3513), [SDL gamepad:3309–3335](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/SDL_gamepad.c#L3309-L3335). Thus **no `11ff` virtual pad at Steam desktop is not, by itself, proof Steam rejected a 1302**; and its *existence* without events is not proof a layout is actively producing input.

**[OpenPuck implementation caution]** Its pinned Puck receiver explicitly stopped treating feature GETs alone as evidence of Steam being in active control; kernel probes and enumerators make GETs without Steam. It instead uses repeated host SET/OUTPUT activity as a **heuristic** [OpenPuck:552–569](https://github.com/safijari/openpuck/blob/29f4d1e8b85c0a7c19e0c8b977a1a56a2c42ea6d/OpenPuck/puck_hid.cpp#L552-L569). Even SET/OUTPUT traffic can come from the kernel at registration, however; periodicity and *process attribution* remain needed on D9. In particular, earlier D9 `0x83` request counts cannot be attributed solely to Steam without such tracing.

### Prioritized owner-only discriminating checks (add to O7)

1. **D9 real versus virtual at identical Steam conditions:** identify current Steam client build, mode (desktop/Big Picture/in-game) and game Steam Input setting. Independently note HID enumeration, active raw handles, Steam listing, presence/emission of virtual `28de:11ff` and what the game itself sees. Separate the **real controller listed** outcome from the virtual **not listed** outcome in #159/#304.
2. **Steam `controller.txt` stage classification:** with private log only, record presence/absence of discovery, managed open, configuration/activation and XInput-slot events. These are *diagnostic patterns*, not required exact strings in every Steam build. Avoid declaring a stage “failed” merely because a log entry format is unknown.
3. **Physical keyboard/mouse continuation:** with `hid-steam` bound, compare mouse/keyboard `0x40/0x41` emission and input-node existence before/while/after a raw client opens. The source predicts HIDINPUT routing **if reports are emitted**; disabled firmware lizard means no input despite the persistent HIDINPUT path.
4. **Close/restoration test:** match `0x85/0x8e` host writes to first returning `0x40/0x41` and repeat at 0,3,5,7,10,15,20 seconds using safe hand movements. Timing after Steam exit alone must be marked *confounded* unless passive bus data rules out host restoration.
5. **Game-specific duplicate check:** evaluate direct native HIDAPI/evdev, Steam virtual `28de:11ff`, and Steam virtual mouse/keyboard **independently**. For native SDL, note `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD`, ignore/except lists and HIDAPI hints privately; for Proton/Wine, game-visible XInput need not imply a corresponding SDL native joystick.

Existing [O7 non-root commands](steam-controller-modes.md#o7-owner-only-d9-observation-checklist-read-only-first-no-root-except-approved-usbmon) remain appropriate. Root **usbmon/tshark** is strictly the physical D9 owner's optional passive operation; it must not be run by this source-only agent. No raw captures, serial numbers, MAC addresses, per-host device paths or firmware images are uploaded. Do not send `0x90`, `0x9f` or update commands.

## Conclusions and boundaries

- **Confirmed in pinned Linux code:** raw-client open alone does not remove the physical HIDINPUT path for mouse/keyboard reports, although it unregisters the native synthetic gamepad/motion devices.
- **Evidence from a different physical transport:** Puck-path lizard returned within about 8 seconds of Steam exit, but host re-registration makes this a **total restoration latency**, *not* isolated proof of a stock watchdog timeout.
- **Source/diagnostic architecture:** distinguish raw recognition, Steam discovery, managed activation, translated output and game visibility. An open hidraw handle or a Steam virtual-device list entry alone is insufficient.
- **Still unknown:** direct-wired retail 1302 autonomous watchdog duration, exact startup persistence of lizard, actual Steam Stable 1792618285 per-game ON/OFF device handback, and the reason D9 UHID wired IBEX is unlisted. Those need owner-controlled D9 comparisons, not emulator code changes on this lane.

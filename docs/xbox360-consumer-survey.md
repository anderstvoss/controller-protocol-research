# Xbox 360 — public software-consumer survey (G)

**Research parity, part 2: consumers and decisions** · **source-only**, not run. Evidence reference: research main after A–F merged; virtualgamepad main `8f60dcce577ab02bd8ed8b3426349729d417393c` was reviewed for the acceptance-model split, not modified. Physical controller identifier: `045e:028e (wired), 045e:0719 receiver`. Consumer inventory ranked by likely acceptance value, **not** probability of successful recognition. Rank does not mean supported.

**Realization semantics:** `linux.uinput` creates evdev nodes only; `linux.uhid.usb` creates a virtual HID bus-visible device with a descriptor which might be bound by `xpad only for native vendor USB interface` or `hid-generic`, exposing hidraw and derived evdev. Neither represents a physical USB controller, RF or XUSB interface. `linux.uhid.bluetooth`, if declared, only presents BUS_BLUETOOTH metadata—not BlueZ pairing. `dummy_hcd`/USB/IP/composite audio is *not* interchangeable with UHID. No USB/IP audio realization is established for this controller; label not-supported/not-measured, never infer audio from controller HID.

**Family-specific sourced behavior:** xpad decodes native XUSB on vendor-specific USB interface and has its own FF/LED; virtualgamepad UHID is deliberately standard HID, decoded via HID usages/evdev and not automatically the SDL XUSB decoder. Pinned claims and sources from part 1: `xbox-series-linux-xpad`, `x360-l0-sdl-hidapi-360-320`, `x360-l0-linux-hid-input`. No physical Xbox, native XUSB via UHID or verified 045e:0719 receiver acceptance; Steam/Eden exact backend No evidence.

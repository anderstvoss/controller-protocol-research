# Decision brief — MotionPlus activation and status-report transitions

**Ranked recommendation:** **(1) (c) a creation-time opt-in compatibility transition** for external MotionPlus, with baseline no-toggle retained. **(2) (b) document and implement a faithful sequence only where source-supported**, currently the WiiBrew-described disconnect then reconnect at deactivation; do not extrapolate to every activation, mode change, or Remote Plus. **(3) (a) keep current no-toggle activation** as baseline, not as a validated retail model. No virtualgamepad code change is authorized by this source-only review.

**Evidence boundary:** Starting research main `e19cadbfea6e` has **210 Wii claims** (including Plus P1); this pass adds **10 source-only claims**, yielding **220** while main is unchanged. Builds on [#46 Dolphin](wii-dolphin-attachment.md), [#47 consumers](wii-motionplus-consumer-comparison.md), [#49 challenge](wii-motionplus-challenge.md), [#51 Remote Plus](wii-remote-plus.md), [#57 Plus traces](wii-remote-plus-consumer-traces.md), [W9e](wii-w9e-generic-retry.md), [W9f](wii-w9f-stimulus.md) and `wii-gap-wiibrew-*`. **No host or hardware runs.** Owner's 2026-10-28 inactive Remote Plus ID decision is A4200005 default, creation-time A6200005 compat; no investigation of that choice.

**F6 conditionality:** Dolphin only requests **A400F6/4** if MotionPlus is **active**, its **embedded downstream-connected bit is true**, and the downstream ID is **unknown**. The ID is cleared by `ProcessExtensionEvent`, invoked on a changed base status bit **or** a changed embedded MP child bit; a subsequent ordinary A400FA read may classify a child first. Thus a base toggle increases F6 reachability but is neither necessary in every trace nor sufficient on its own. See `wii-gap-mpstatus-dolphin-ciface-f6-edge` and earlier `wii-gap-dolphin-attach-passthrough-four-byte-id-f6`.

## Q1. Community documentation: what is and is not established

The pinned [WiiBrew MotionPlus oldid 120079](https://wiibrew.org/w/index.php?title=Wii_Motion_Plus&oldid=120079) and `wii-gap-wiibrew-motionplus-id-and-activation` identify A600FE **04** standalone, **05** Nunchuk, **07** Classic-family, with mapped A400FA IDs ending respectively 04 05, 05 05, 07 05. `wii-gap-wiibrew-motionplus-deactivation` documents **A400F0=55 deactivation** with **two 0x20 status transitions, disconnected then reconnected**, restoring downstream access. The [WiiBrew Wiimote oldid 123257](https://wiibrew.org/w/index.php?title=Wiimote&oldid=123257) and `wii-gap-wiibrew-status-20-resend` describe **0x20** as 0x15 response **and unsolicited attachment notification**, status extension bit **0x02**, and data-report **0x12** reselection after port change.

**Not documented sufficiently by these pinned records:** exact 0x20 edge count/order for **activating A600FE=04/05/07**, **switching active 04/05/07**, and **inserting/removing child while MP is active**; numeric device transition delays; whether a Remote Plus behaves identically. WiiBrew describes MP embedded downstream connectivity, not a guaranteed base-0x20 event for every child change. The deactivation pair is **community-described**, not a newly measured retail trace; do not infer it in all accessory-presence conditions. No new inaccessible WiiBrew page is needed; existing pinned oldids/hashes are reused. Source IDs: `wii-gap-wiibrew-motionplus-oldid120079`, `wii-gap-wiibrew-wiimote-oldid123257`, `wii-gap-wiibrew-extensions-oldid121955`.

## Q2. Dolphin emulated model versus retail hardware

At pinned Dolphin [MotionPlus.cpp 322–389](https://github.com/dolphin-emu/dolphin/blob/3eb30c7620b4475b2e0404228ba0d2b238a132f1/Source/Core/Core/HW/WiimoteEmu/MotionPlus.cpp#L322-L389), activation/deactivation temporarily set the **device-detect pin false** for an emulator-chosen **20 ms**. After activation, it becomes **true**; after deactivation, it proxies downstream extension presence. The emulated [WiimoteEmu.cpp 429–447](https://github.com/dolphin-emu/dolphin/blob/e1d35f666cc35f6ead55d32ea2679df44d04da72/Source/Core/Core/HW/WiimoteEmu/WiimoteEmu.cpp#L429-L447) detects changed pin state, sends **unsolicited 0x20**, and stops data reports until another **0x12**. With downstream connected at both endpoints: activation or deactivation models **disconnect → reconnect**. With no downstream child: activation gives a **single connect** and deactivation a **single disconnect**. Actual delivery timing is bounded by emulation updates, not a fixed physical measured delay.

**Active mode switches** among 04/05/07 do not restart activation when already active, hence **no intrinsic status pulse** in this emulator. While active, downstream plug/unplug changes the **embedded MotionPlus child-connected bit**, while the base detect pin remains true; [MotionPlus.cpp 394–465](https://github.com/dolphin-emu/dolphin/blob/3eb30c7620b4475b2e0404228ba0d2b238a132f1/Source/Core/Core/HW/WiimoteEmu/MotionPlus.cpp#L394-L465) explicitly labels its internal downstream initialization approximate. Source comments mention real hardware, but there is **no attributable physical timestamped capture** here. The emulator and Dolphin ControllerInterface are not independent physical measurements.

Independent [wiiuse activation/deactivation](https://github.com/wiiuse/wiiuse/blob/e769bd73860a4f941bd110ebae5a790f968b71e3/src/motion_plus.c#L170-L235) sleeps **500 ms** on each switch and after deactivation polls 0x20 up to three times (with further host waits) before proceeding. These are **host-side waits and retries**, not measured MotionPlus hardware delays or evidence of unsolicited edges.

## Q4. Implications for virtualgamepad

A synthetic disconnect/reconnect edge may unlock Dolphin's F6 identity-mirror path, but a changed **MP embedded child bit** can also clear the ID independently and may be a more faithful trigger for a particular trace. Edge-driven report-mode resets may cause **0x12** to be resent. Do not conflate that with W9f's separate proven behavior: after mode 05, **zero post-map MP/child reports** were counted because the current codec awaited a fresh 0x12 and Dolphin did not send one in that arm (`wii-w9f-dolphin-motionplus-nunchuk-on-result`). A toggle could change the result without proving a hardware requirement. The F6 mirror is needed **if** F6 is actually requested, not automatically on all MP activations.

A **bounded creation-time compat switch** should be tested against current no-toggle control without changing kernel binding. Record exact 0x15/0x20/0x12 sequences, A400F0/A600FE actor writes, A400FA/F6 reads, errors, worker scheduling and SDL reinit by mode. Never emit repeated edge trains to force a consumer through F6: Linux may reinitialize A400 and deactivate MP, and SDL can reset extension state; W9 kernel contention is an explicit regression risk, not an observed outcome of this unrun change.

## Q5. Minimal deferred physical capture — **not run**; append to #52

Run on **(1)** an original retail Wii Remote with external MotionPlus and **(2)** a Wii Remote Plus, without disclosing identities or unverified firmware details. An owner-controlled logger distinguishes requested (0x15-induced) versus unsolicited 0x20, captures relative timestamps, bit 0x02, 0x16 writes/0x22 ACKs, 0x17 reads/0x21 replies, 0x12 mode and report delivery. Keep raw captures private; publish sanitized counts and bounds only.

1. From idle with **no child**, request baseline 0x15, select 0x12, write **A600F0=55**, activate **A600FE=04**; count 0x20 edges, statuses and reporting resumption. Repeat with Nunchuk/Classic preattached using **05/07**, without confusing solicited 0x20 with spontaneous events.
2. From active mode, switch **04↔05↔07** and deactivate **A400F0=55**; count exact disconnect/reconnect order, relative delays and whether another 0x12 is required.
3. While active, plug/unplug downstream child and compare base 0x20 versus **embedded MotionPlus child-connected bit** and any A400FA/F6 results or errors. Repeat minimal cases separately per device revision.
4. Use a second controlled consumer observation only after isolated wire traces to distinguish kernel re-probes, SDL reinitialization and Dolphin F6 reachability from actual hardware status generation.

**All proposed experiments are not run.** This is not a calibration, encrypted challenge, radio, or physical acceptance finding. No GPL excerpts, firmware/ROM, MAC, serial or identifying captures are included.

# Switch 2 Joy-Con — post-Alpha 2 starter research

Source-only review for [virtualgamepad #362](https://github.com/anderstvoss/virtualgamepad/issues/362). **No host, controller hardware, Bluetooth pairing, native USB descriptor, firmware, or virtual-provider tests were run.** The source implementations below are consumer expectations, not physical captures.

## Source pins and protocol/consumer detail

The Linux references reuse already-pinned corpus source records `switch2-gc-linux-hid` (full SHA `77c7155e2707ba5b1d56f3dc1acead48cf17f98d`, `drivers/hid/hid-nintendo.c`, SHA-256 `24c36517d7030a3fb5d46131314e356cca931562c55bf028bb091dd4690c360d`) and `switch2-gc-linux-usb` (`9417132df63e5cd7230433af05198538e759f3ae`, `drivers/hid/hid-nintendo-switch2-usb.c`, SHA-256 `c0bed151d80471552ec7cb0a0254a4084e00ec2cf99fde5da88aa5214cde2bb4`). Those two files are **one Linux lineage**, at different pins. Linux code is GPL-2.0-or-later / kernel SPDX as applicable; no upstream source is reproduced here. New separately hashed source records cover the [Linux product IDs](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-ids.h#L1115-L1122), [SDL identities](https://github.com/libsdl-org/SDL/blob/fe2bca9748afa754ebbca4c543c5b28bbce30cf4/src/joystick/usb_ids.h#L125-L134) and [SDL gamepad mapping](https://github.com/libsdl-org/SDL/blob/fe2bca9748afa754ebbca4c543c5b28bbce30cf4/src/joystick/SDL_gamepad.c#L1134-L1157). SDL is zlib-licensed. SDL's driver source `sdl-switch2` and the existing `switch2-gc-sdl-libusb` source record are reused where they pin the inspected file and revision.

**Identity and units.** The [Linux USB HID match table](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L4442-L4479) and [USB configuration-interface match table](https://github.com/torvalds/linux/blob/9417132df63e5cd7230433af05198538e759f3ae/drivers/hid/hid-nintendo-switch2-usb.c#L471-L480) name left and right separately. SDL [recognizes distinct left and right products](https://github.com/libsdl-org/SDL/blob/fe2bca9748afa754ebbca4c543c5b28bbce30cf4/src/joystick/hidapi/SDL_hidapi_switch2.c#L308-L320), while its [default mapping also has a pair entry](https://github.com/libsdl-org/SDL/blob/fe2bca9748afa754ebbca4c543c5b28bbce30cf4/src/joystick/SDL_gamepad.c#L1134-L1157). The pair mapping is not a captured native `0x2068` USB device. Default to two independent instances with separately caller-configurable identities; a paired application view should be consumer- or receiver-level, as for Switch 1. Do not mint a native combined USB personality without evidence.

**Transport and initialization.** [Linux's Switch 2 HID probe](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L4336-L4410) explicitly requires USB and shares state with a vendor-class configuration interface; its [initialization flow](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L4107-L4185) requests firmware information, selected calibration, enabled features, grip-side controls and side-specific report formats. Its companion [USB driver](https://github.com/torvalds/linux/blob/9417132df63e5cd7230433af05198538e759f3ae/drivers/hid/hid-nintendo-switch2-usb.c#L340-L422) finds bulk endpoints on the selected interface instead of hard-coding endpoint numbers. SDL [discovers bulk endpoints on interface 1](https://github.com/libsdl-org/SDL/blob/fe2bca9748afa754ebbca4c543c5b28bbce30cf4/src/joystick/hidapi/SDL_hidapi_switch2.c#L323-L390) and carries out command/read setup over libusb. SDL's [HIDAPI backend whitelist](https://github.com/libsdl-org/SDL/blob/d6fbbbe14dddfa09d6168267a0fcd39dea5a398a/src/hidapi/SDL_hidapi.c#L774-L800) explicitly includes both halves (source `switch2-gc-sdl-libusb`, zlib). These pins establish native USB consumer expectations but **not** how retail Joy-Con 2 connects physically while docked, attached or charging.

**Reports and evdev.** Linux [assigns per-side report identifiers](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L3040-L3053) 0x07 and 0x08, and [handles each plus unified 0x05](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L3933-L4042). In the per-half input paths, button data begin at offset 3 and the packed 12-bit stick at offset 6; the unified paths have different offsets. Linux [exposes one signed stick and side-specific button set per half](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L3180-L3244) [at evdev initialization](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L3585-L3671); native right C becomes `BTN_C`. The Linux consumer initializes conditional ordinary `FF_RUMBLE`, which cannot by itself establish HD-rumble equivalence. SDL [maps USB packets as either vertical/paired or mini orientation](https://github.com/libsdl-org/SDL/blob/fe2bca9748afa754ebbca4c543c5b28bbce30cf4/src/joystick/hidapi/SDL_hidapi_switch2.c#L773-L940) and [has sensor handling and per-side orientation transforms](https://github.com/libsdl-org/SDL/blob/fe2bca9748afa754ebbca4c543c5b28bbce30cf4/src/joystick/hidapi/SDL_hidapi_switch2.c#L1113-L1241). Do not assume SDL raw report fields, Linux evdev values and physical on-air values are the same interface.

**Mouse and Bluetooth.** The kernel [defines a mouse feature bit](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L2991-L2996) but its [enabled features](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L4141-L4146) and [input parsing](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L3933-L4042) do not expose mouse motion. The reviewed SDL Switch 2 joystick file has no mouse processing; that limited absence does not establish a global SDL or OS capability statement. SDL [explicitly rejects Switch 2 Bluetooth in this implementation](https://github.com/libsdl-org/SDL/blob/fe2bca9748afa754ebbca4c543c5b28bbce30cf4/src/joystick/hidapi/SDL_hidapi_switch2.c#L323-L327), and Linux [rejects non-USB Switch 2 HID probe](https://github.com/torvalds/linux/blob/77c7155e2707ba5b1d56f3dc1acead48cf17f98d/drivers/hid/hid-nintendo.c#L4336-L4345). No Switch 1 Bluetooth report compatibility or simulated radio pairing is established. Physical mouse report format, activation and output semantics remain unknown.

## Realization decision

1. **First: playable per-half `linux.uinput`.** Expose the supported evdev buttons and one stick on each independent device; preserve right C, side-specific grip controls and per-instance identity in the controller API. Map only representable ordinary rumble where a provider actually supports it. Label unsupported motion, native USB identity, rail behavior, mouse sensor and HD-rumble fidelity explicitly. This creates generic playable events, not a native Joy-Con 2 USB personality.
2. **Next: faithful USB prototype only after provider work.** The current `RealizationId` registry names `linux.uhid.usb`, `linux.uhid.bluetooth`, `linux.dummy_hcd.usb-hid`, `linux.usbip.usb-audio`, and `linux.uinput` ([pinned virtualgamepad registry](https://github.com/anderstvoss/virtualgamepad/blob/8cd1000a308eac682eca43d766b0f1a1f71a6f1e/crates/gr-realization-api/src/lib.rs#L40-L47)). UHID alone cannot create a vendor-specific USB bulk interface, the current dummy_hcd contract is fixed-purpose HID ([provider pin](https://github.com/anderstvoss/virtualgamepad/blob/8cd1000a308eac682eca43d766b0f1a1f71a6f1e/crates/gr-provider-linux-dummy-hcd/src/lib.rs#L1-L45)), and the named USB/IP provider is USB audio. A new/extended composite USB gadget or USB/IP provider would be necessary; feasibility and host recognition are **not tested**. Do not treat a BUS_USB UHID node as a validated replacement for a real USB device.
3. **Bluetooth remains an independent research lane.** Neither pinned native consumer path gives a demonstrated Switch 2 Bluetooth-bus UHID acceptance route. Do not recycle the Switch 1 Joy-Con protocol or claim working Bluetooth pairing.

The findings are consistent with [virtualgamepad's controller-family modeling guide](https://github.com/anderstvoss/virtualgamepad/blob/8cd1000a308eac682eca43d766b0f1a1f71a6f1e/docs/spec/implementation/CONTROLLER_FAMILY_MODELING.md): native controls remain native, while missing realizations are reported instead of silently degraded. Runtime controller creation should allow caller-specified instance identity. No source or fixture establishes physical identity values.

## Proposed tests, not run

- **Physical scope and identity:** On a user-controlled setup, separately enumerate each half over supported wired attachment methods and Bluetooth; record only sanitized device-level capability summaries and the fact of separate versus combined nodes. Record exact host/kernel/SDL revisions, but never publish identifying values or sensitive device material.
- **USB consumer proof:** With a future composite USB provider, test vendor-class interface and bulk endpoint discovery, command acknowledgments, correct left/right firmware-type selection, side reports 0x07 / 0x08 and unified 0x05 handling, hotplug/removal, and SDL libusb enumeration. Validate that neither a plain UHID node nor the present HID-only dummy_hcd path is accidentally labeled faithful.
- **Playable evdev:** Create each `linux.uinput` instance; compare buttons, one-stick signed range, C and SL/SR events, conditional rumble and creation/removal cleanup against the pinned Linux source shape. Confirm SDL generic fallback separately from native HIDAPI acceptance.
- **Motion and mouse:** Measure actual per-half motion orientation, report cadence, calibration fallback, mouse motion activation/output and any standalone/combined SDL behavior. Preserve mouse as its own capability, not a fabricated stick or touch axis.
- **Bluetooth/receiver:** Only after a separate transport specification exists, evaluate radio/pairing, reconnect, host binding and native pair aggregation. Keep the pair as two units unless evidence shows a real receiver personality.

**Disposition:** Source-only starter; implementation, physical fidelity, vendor-specific USB emulation, Steam support and native Switch 2 Bluetooth recognition are **unvalidated**.

## 1. Scope and decisions

This is **source-only consumer research**, not a captured Xbox One protocol, host test or device validation. The exact pinned Linux commit is `4056b3c9d3c92ea45955641dbafeb9b960e146ef`, SDL commit `d4557c1511c721485dc4960f7149730afc9a73a0`, and xpadneo commit `56b538d951300bf804f6631738603c5eb14c04f0`. The first two commits are the same source versions already used in the Xbox Series corpus. A new full-file hash record exists only for SDL's core joystick classifier; all other same-revision source records are reused. No GPL text or upstream packet dumps are copied.

**Recommendation:** Xbox One is a distinct curated family, not a Series package variant. Preserve a common internal xpad-compatible input projection only when native control units and semantics match. The absence of Share is a native capability difference, not a fabricated always-released Series key. Use variants for Microsoft original/2015 and One S identity/report capability decisions, with explicit refusals for unresolved transports. Caller-specified identity must be honored at creation; do not infer a physical unit identity from source-only samples.

## 2. Wired USB: consumer identity and emitted evdev shape

At [xpad lines 127–134](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/input/joystick/xpad.c#L127-L134), standard Xbox One, 2015-firmware Xbox One and One S Microsoft USB identities all use the Xbox One driver type without Share. Series uses the same driver type with Share and a different source bit offset. The included Elite / Adaptive rows have their own paddle/profile flags and **are not part of this first standard Xbox One profile**. Xbox One compatibility should not inherit Series Share or Elite paddle capabilities merely because all have `XTYPE_XBOXONE`.

From [xpad axis and input setup](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/input/joystick/xpad.c#L1905-L2033) and [input decoding](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/input/joystick/xpad.c#L1095-L1159), the ordinary Microsoft Xbox One path supplies `BTN_A`, `BTN_B`, `BTN_X`, `BTN_Y`, `BTN_TL`, `BTN_TR`, `BTN_SELECT`, `BTN_START`, `BTN_MODE` and both stick-click keys. `ABS_X/Y/RX/RY` are signed −32768–32767 with kernel fuzz 16 and flat 128; `ABS_Z/RZ` are 0–1023; `ABS_HAT0X/Y` range −1–1. Stock xpad supports main-motor force feedback, with memoryless FF capability details already recorded as `xbox-series-xpad-evdev-shape` and `xbox-series-xpad-trigger-rumble-limitation`. Those Series records are shared *driver evidence*, not proof of Xbox One reference hardware.

The [real USB probe](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/input/joystick/xpad.c#L2056-L2132) and [initialization table](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/input/joystick/xpad.c#L642-L659) are wired GIP-specific, including an Xbox One S conditional startup step. A uinput node only offers the decoded Linux input surface. It has no genuine USB interface, GIP negotiation, authenticated behavior, audio interface or Xbox Wireless Adapter. Never create a fake USB HID device and call it GIP. The receiver is tracked separately in virtualgamepad #168.

## 3. Bluetooth revisions and Linux/SDL consumers

Pinned [kernel HID IDs](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/hid/hid-ids.h#L1052-L1060) and [Bluetooth driver table](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/hid/hid-microsoft.c#L427-L435) match model 1708 using the two distinct Bluetooth PIDs 0x02fd and 0x0b20. This is not the same transport as USB `xpad`; available HID drivers and active binding policy vary by host. These source rows do **not** independently establish Bluetooth availability on the original Xbox One revision or the exact firmware transition for an actual One S unit. Verify those against an owner reference, not a guessed descriptor.

SDL's [older-ID table](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/SDL_joystick.c#L127-L148) includes both One S Bluetooth identities as non-Share, while its [Share helper](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/SDL_joystick.c#L3382-L3406) otherwise defaults to treating unlisted Xbox-style controllers as Share-capable. The [Xbox One HIDAPI driver](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/hidapi/SDL_hidapi_xboxone.c#L364-L468) assigns Xbox One-family gamepad behavior, supports Linux HID descriptor parsing when the descriptor is acceptable, and switches to transport-specific fallback if not. Its [open path](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/hidapi/SDL_hidapi_xboxone.c#L496-L520) uses eleven buttons for known old models, versus twelve when Share is present. The [Bluetooth fallback](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/hidapi/SDL_hidapi_xboxone.c#L1256-L1311) documents a 16-byte 3.1.1221 state and later 17-byte 4.8.1923 / 5.x cases; Guide can be separate or inline. [Report dispatch](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/hidapi/SDL_hidapi_xboxone.c#L1955-L1998) distinguishes state ID 0x01, Guide ID 0x02 and battery ID 0x04. These are SDL consumers' expected formats, not a validated native universal report.

The [xpadneo BLE-era caveat](https://github.com/atar-axis/xpadneo/blob/56b538d951300bf804f6631738603c5eb14c04f0/docs/README.md#L88-L97) says a shared non-Elite-Series-2 BLE descriptor can advertise a Share field even where hardware lacks it. The [model 1708 source examples](https://github.com/atar-axis/xpadneo/blob/56b538d951300bf804f6631738603c5eb14c04f0/docs/descriptors/xb1s_linux.md#L3-L43) differ in descriptor length and Linux-mode presentation. Therefore a Series HID descriptor, an older 1708 example, or a Share bit inferred from BLE is not an acceptable ready-made faithful Xbox One UHID profile. Optional xpadneo modifies Linux input and has distinct HID output/permission behavior, already bounded in `xbox-cgap-*` records.

## 4. First implementation and explicit limits

Implement a standalone Xbox One curated package with native inputs A/B/X/Y, bumpers, View, Menu, Guide, stick clicks, two trigger values, two signed sticks and D-pad. Omit native Share in standard Xbox One revisions. Keep model/firmware identity options explicit and reject unknown variant-specific claims. The selected `linux.uinput` realization uses the source-backed xpad event codes, axis domains and standard no-Share key topology, not the existing Series 26-capability golden unchanged. Document deviations if chosen uinput flags, fuzz, flat, FF capabilities, identity naming or version differ. Run the SDL evdev acceptance independently and never mark it complete from this research.

Rumble via ordinary FF may be playable; separate impulse-trigger motors are not independently addressable through xpad's conventional evdev API, even if a driver translates to a richer native output. Audio, battery, LEDs, pairing and wireless physical behavior are not reproduced by a plain gamepad uinput device. A future `linux.uhid.bluetooth` should be scoped to physically Bluetooth-capable revisions, with correct descriptor, input and reverse-output policy, and **does not** provide actual Bluetooth radio discovery or pairing.

Cross-project realization identifiers are `RealizationId::LINUX_UINPUT` and (future only) `RealizationId::LINUX_UHID_BLUETOOTH`; no other realization is claimed. Implementation in virtualgamepad, status promotion and per-instance identity policy belong to the project issue, not this corpus PR.

## 5. Proposed tests, not run

1. **USB reference matrix:** owner collects safe, non-identifying model/firmware and active driver selection for original, 2015 USB and One S, testing one revision at a time; compare xpad key/ABS/FF capabilities and values to the published driver shape.
2. **Synthetic uinput consumer:** build the no-Share profile with each requested identity, verify eleven key capabilities, all eight axes and domains, Guide/View/Menu, neutral state, main rumble and explicit refusal of unsupported outputs. Record any difference from xpad's FF and fuzz.
3. **SDL acceptance:** test SDL 3 with HIDAPI enabled and disabled, identifying whether evdev or HIDAPI actually opens, reporting Gamepad mapping for all controls, Share absence, and create/remove behavior. Compare the Series uinput baseline only as a separate control arm.
4. **Bluetooth reference by firmware:** only on genuine supported One S units, privately review descriptor hash/length, HID match, input/Guide/battery and report lengths, Classic-versus-BLE path, SDL descriptor-versus-fallback behavior and xpadneo differences; do not publish identifying traffic or bytes.
5. **UHID feasibility after evidence:** exercise only a validated model/firmware descriptor over local Bluetooth-bus UHID, including output request/reply, driver ownership and teardown; do not confuse local UHID with physical radio pairing.
6. **Lifecycle and regressions:** repeated creation/removal, concurrent per-instance identities, permission failures and rollback with no leaks; collect measured timings against #166 before setting budgets.

**Results: none run.** No controller, Linux host or Bluetooth hardware was available. Device behavior and faithful-transport capability remain unknown.

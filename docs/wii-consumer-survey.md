# Wii Remote software-consumer survey: independent acceptance candidates

**Evidence date:** 2026-10-23. **Baseline:** research `main` `780f87da9ecc25b1e6a1e8e6295e66ab1ebbca7b` (119 Wii claims before this PR); W5 research [#35](https://github.com/anderstvoss/controller-protocol-research/pull/35) / [diagnosis](https://github.com/anderstvoss/controller-protocol-research/blob/main/docs/wii-w5-gyro-diagnosis.md) showed two kernel MotionPlus delivery passes with A600FE 04/05, and blocked SDL 3.2.10 gyro and Dolphin direct-input consumer paths. **This survey is source analysis, not a host run.** All proposed tests below are **not run**.

**Transport models:**
- `linux.uhid.bluetooth` realizes a Linux HID object with bus `BUS_BLUETOOTH`, Nintendo `057e:0306`, `hid-wiimote` binding, real `hidraw`, and kernel-created Wii evdev interfaces. It **does not** create a physical RF radio identity, an L2CAP control/interrupt server, or Bluetooth adapter passthrough.
- `linux.uinput` realizes evdev input interfaces mimicking some `hid-wiimote` core and extension nodes. It does **not** automatically create a HID parent, matching `wiimote` kernel-driver binding, `hidraw`, Bluetooth L2CAP, sysfs LEDs/power-supply, or distinct device ownership/hierarchy identical to the kernel.
- An entry **yes, conditional** means the source's *discovery path could reach it*, not that the app successfully connects or every feature works. **No** means its required entrypoint is absent. Sensor node name, permission, udev tag, parent, VID/PID, selected driver and report mode remain separate acceptance gates.

## Consumer implementation notes

### 1. xwiimote, libxwiimote and xwiishow — MIT-like permissive license

Pinned xwiimote `4df713d9037d` [core](https://github.com/xwiimote/xwiimote/blob/4df713d9037d814cc0c64197f69e5c78d55caaf1/lib/core.c#L345-L380), [interface names](https://github.com/xwiimote/xwiimote/blob/4df713d9037d814cc0c64197f69e5c78d55caaf1/lib/xwiimote.h#L230-L260), [monitor](https://github.com/xwiimote/xwiimote/blob/4df713d9037d814cc0c64197f69e5c78d55caaf1/lib/monitor.c#L35-L70), [xwiishow UI](https://github.com/xwiimote/xwiimote/blob/4df713d9037d814cc0c64197f69e5c78d55caaf1/tools/xwiishow.c#L2603-L2730); [license](https://github.com/xwiimote/xwiimote/blob/4df713d9037d814cc0c64197f69e5c78d55caaf1/LICENSE#L1-L21).

- **Discovery:** monitor enumerates sysfs HID parents; `xwii_iface_new` additionally checks that the **bound Linux driver name is `wiimote`** and expected HID properties exist. It discovers a Wii's `input*/event*` child nodes and checks the exact names (core, accelerometer, IR, Motion Plus, Nunchuk, Classic Controller, etc.) before opening them ([core driver gate](https://github.com/xwiimote/xwiimote/blob/4df713d9037d814cc0c64197f69e5c78d55caaf1/lib/core.c#L345-L380), [open](https://github.com/xwiimote/xwiimote/blob/4df713d9037d814cc0c64197f69e5c78d55caaf1/lib/core.c#L545-L660)). **It does not work with just *any* generic event device**, nor every device the kernel driver binds if needed child names/permissions are absent.
- **MotionPlus ownership:** `xwii_iface_open(...XWII_IFACE_MOTION_PLUS...)` opens the dedicated kernel evdev node, triggering `hid-wiimote`'s `MP_USED` path when the kernel node is real. Source [gyro reader](https://github.com/xwiimote/xwiimote/blob/4df713d9037d814cc0c64197f69e5c78d55caaf1/lib/core.c#L1040-L1104) consumes `ABS_RX/RY/RZ` as angular velocity. libxwiimote does **not** issue raw A600FE writes, read MotionPlus EEPROM calibration, validate native checksum or parse six-byte raw fields.
- **Normalization:** its exposed axes are **kernel-valued units, not calibrated SI angular velocity**. Its optional `set_mp_normalization` subtracts three offsets, while an adjustable factor slowly moves those offsets as new samples arrive. `xwiishow` implements an interactive stabilization refresh after an initial high-variance interval. No persistent hardware calibration file/CRC protocol is evidenced by these functions.
- **Other IO:** separate evdev accel/IR/extension nodes and sysfs LED/battery; optional FF_RUMBLE on core. Speaker is not supported by this library path. A real `hid-wiimote` sysfs ancestry is relevant; synthetic uinput named event nodes alone do not satisfy its discovery model.
- **Host test (not run):** with an owner-authorized exact-created UHID, run `xwiishow list`; open displayed index with `xwiishow 1` (or exact sysfs HID path, **not a guessed index**); toggle `m`, `a`, `i`, `n` and LED toggles, exercise Nunchuk/Classic where attached. Pass: the owned HID enumerates under expected names; gyro data change with driven signed rotation, and zero-offset normalization changes as expected while motionless. Fail boundaries: if no listing, inspect `wiimote` driver and sysfs child/name; if listed but no gyro, verify MP event FD open and kernel A600FE 04/05. **Do not run privileged scans or device unbind.**

### 2. Cemu native Wii U emulator input — MPL-2.0

Pinned Cemu `29f2f1fae463`, [SDL3 HIDAPI filter](https://github.com/cemu-project/Cemu/blob/29f2f1fae4631e2317977debd9eacd55cc28dd7d/src/input/api/Wiimote/hidapi/HidapiWiimote.cpp#L5-L47), [connection/reader](https://github.com/cemu-project/Cemu/blob/29f2f1fae4631e2317977debd9eacd55cc28dd7d/src/input/api/Wiimote/WiimoteControllerProvider.cpp#L59-L275), [native extension and gyro](https://github.com/cemu-project/Cemu/blob/29f2f1fae4631e2317977debd9eacd55cc28dd7d/src/input/api/Wiimote/WiimoteControllerProvider.cpp#L243-L390), [gyro parser](https://github.com/cemu-project/Cemu/blob/29f2f1fae4631e2317977debd9eacd55cc28dd7d/src/input/api/Wiimote/WiimoteControllerProvider.cpp#L470-L548), [register definitions](https://github.com/cemu-project/Cemu/blob/29f2f1fae4631e2317977debd9eacd55cc28dd7d/src/input/api/Wiimote/WiimoteMessages.h#L29-L63); [MPL-2.0 confirmation](https://github.com/cemu-project/Cemu/blob/29f2f1fae4631e2317977debd9eacd55cc28dd7d/README.md#L50-L66).

- **Entry:** when compiled with `HAS_HIDAPI`, Cemu enumerates HID paths via SDL3 `SDL_hid_enumerate(0x057e, 0)`, keeps PIDs **0306 or 0330**, excludes named Wii U Pro Controller, and opens its path nonblocking. There is no bus-type rejection in this specific filter. With `HAS_BLUEZ` it *also* supports a separate L2CAP backend, which **cannot** be created by the UHID device alone. The app must actually enable/use the native Wiimote controller API rather than only the generic SDL gamepad API.
- **Open and feature handshakes:** its provider starts threads, performs a **status-request write** when registering a discovered device, then on status initializes IR, reads eight bytes of accelerometer EEPROM calibration, probes MotionPlus and checks extension bit/identity. Extension identity reader recognizes Nunchuk, Classic, Classic Pro and MotionPlus. It writes extension-init registers and can read 16 bytes of accessory calibration.
- **MotionPlus:** on a recognized mapped MP identity its source sends MotionPlus initialization and A600FE **04** activation. Its gyro parser exists in **report 0x37** (core+accel+IR+extension), extracting three 14-bit fields and slow flags, but its state/extension dispatch, report-type selection and calibration code do **not** establish an end-to-end decoder path in every mode. Its MotionPlus calibration transform is currently not applied in the reviewed parser; **do not assert calibrated physical radians/sec or gyro pass**. Its automatic remapping of Nunchuk pass-through with MP is **not proven** in this branch.
- **Other features:** buttons, accel, IR, Nunchuk/Classic, LED, rumble; speaker sending/consumption not verified. EEPROM base accel read is real code; MotionPlus calibration checksum validation **not evidenced**.
- **Host test (not run):** launch exact pinned/locally available Cemu with the user-selected **native Wii Remote input API** (not SDL generic); keep a single owned UHID only. Trace SDL HIDAPI enumerate/open → status write/read → 8-byte EEPROM read → MotionPlus identity at A600FA → A600F0 reset → A600FE 04 map → 0x12 report-mode selection → 0x37 gyro frames. Observe whether Cemu creates a usable input device and reports changing gyro and extensions to its native-controller state/UI; use instrumented status output if UI does not expose gyro. Separate **discovery/handshake failure**, **reports not reaching decoder**, **wrong gyro transform**, and **kernel/consumer register races**. Compare kernel bound versus any alternative binding **only after owner authorization**, not during this survey.

### 3. Dolphin — GPL-2.0-or-later; supplement to existing claims

**Do not duplicate** `wii-gap-dolphin-hidapi-kernel-binding-competition`, `wii-gap-dolphin-controllerinterface-motionplus-calibration-gate`, `wii-gap-dolphin-real-remote-path-separation`, `wii-w5-dolphin-*`. This survey adds only `wii-gap-consumer-dolphin-hidapi-usability-probe` as a genuinely distinct discovery gate.

Pinned [Real Wii Remote HIDAPI scanner](https://github.com/dolphin-emu/dolphin/blob/e1d35f666cc35f6ead55d32ea2679df44d04da72/Source/Core/Core/HW/WiimoteReal/IOhidapi.cpp#L17-L163): (1) enumerate all HID paths, (2) validate product **name or known VID/PID** and unused path, (3) temporarily open with `hid_open_path` and **write a native status request** as its `IsDeviceUsable` test, (4) close the temporary handle and construct a candidate device, (5) subsequently open again at `Connect`, (6) add to ControllerInterface only after connection and preparation [ControllerInterface AddDevice](https://github.com/dolphin-emu/dolphin/blob/e1d35f666cc35f6ead55d32ea2679df44d04da72/Source/Core/InputCommon/ControllerInterface/Wiimote/WiimoteController.cpp#L105-L151). It has no absolute BUS_BLUETOOTH prohibition in this scanner path, but warns that `hid-wiimote` can fight its own register writes; this log does **not** automatically unbind the kernel. Emulator's real Bluetooth L2CAP and Bluetooth-adapter passthrough are separate.

W5's installed Flatpak had a raw path that the agent could open, but **recorded no Dolphin direct backend I/O or connection**. This does not prove `IsDeviceUsable` failed: absence of trace may mean scanner excluded name/ID, Flatpak access/portal filtering, backend selection/slot state, or test observation limitations. None is established. **Proposed local test, not run:** enable exact owned-device Dolphin HIDAPI scanner trace with raw-path enumeration, `IsDeviceUsable` write/return, `ConnectInternal` return, `AddDevice` result; then capture status/extension mode and MotionPlus calibration at offset 0x20 if ControllerInterface actually opens. Exclude real Bluetooth pairing and adapter passthrough. Dolphin's ControllerInterface requires gyro calibration; Cemu and SDL make different decisions. A separate raw FD opening is not the Dolphin acceptance oracle.

### 4. RetroArch/libretro and other udev/evdev consumers — GPL-3.0-or-later for RetroArch

Pinned RetroArch `1bbd7eda123a` [udev source](https://github.com/libretro/RetroArch/blob/1bbd7eda123acea17cbea15de48bea4fdb21a68d/input/drivers_joypad/udev_joypad.c#L556-L799); [sibling-sensor selection](https://github.com/libretro/RetroArch/blob/1bbd7eda123acea17cbea15de48bea4fdb21a68d/input/drivers_joypad/udev_joypad.c#L556-L799), [event processing](https://github.com/libretro/RetroArch/blob/1bbd7eda123acea17cbea15de48bea4fdb21a68d/input/drivers_joypad/udev_joypad.c#L1430-L1487), [sensor enable](https://github.com/libretro/RetroArch/blob/1bbd7eda123acea17cbea15de48bea4fdb21a68d/input/drivers_joypad/udev_joypad.c#L1700-L1759).

- **Joypad entry:** opens `ID_INPUT_JOYSTICK=1`-tagged `/dev/input/event*` nodes, maps `EV_KEY` buttons and `EV_ABS` sticks/axes and attempts FF_RUMBLE. The relevant pad may be a Wii core (buttons) or supported downstream Classic pad, depending on udev classification. It neither recognizes Wii register identities nor activates MotionPlus itself.
- **Sensor sibling:** finds a single sensor under the **same HID sysfs parent**. Preferred scan requires `ID_INPUT_ACCELEROMETER`; fallback scans matching input event children when hid-wiimote accelerometer is untagged. It **stops after the first candidate**, making node order and lab udev tags material. An RXYZ-only node is hard-coded to mean Wii **accelerometer**, with `sensor_has_gyro=false`. So the kernel's **MotionPlus gyro** RXYZ-only node may be misclassified and gyro sensor activation rejected; do not conflate Wii accelerometer RXYZ with M+ RXYZ (same codes, different named node).
- **uinput:** if its event node is tagged joystick, generic controls can appear. Without a shared HID ancestor it cannot use the **same parent matching** as the UHID sibling-sensor algorithm. Even if custom `/dev/input/event*` axes are present, libretro SENSOR_GYRO values are not guaranteed.
- **Host test (not run):** select `udev` joypad driver in RetroArch, start `retroarch --verbose`, observe recognized device, compare button/axis state, inspect whether a loaded sensor-aware libretro core sees `RETRO_SENSOR_GYROSCOPE_ENABLE` success. Repeat UHID and uinput. Pass core input independently from gyro. Before filing issues or modeling fixes, determine which sibling node was opened (accelerometer versus MP) and whether the RXYZ-only Wii branch was taken. No raw HID MotionPlus support follows.

**Other generic clients:** AntiMicroX pinned [SDL2 inputdaemon](https://github.com/AntiMicroX/antimicrox/blob/b5fb5947d67b4505c6404da17766130c9102178c/src/inputdaemon.cpp#L170-L195) uses SDL gamepad/joystick open; good basic button/axes remapper, not independent MotionPlus decoder. Vanilla `evtest` and `libevdev` readers directly open whichever event node is passed and display its `EV_ABS` values; their successful read confirms **kernel/uinput event delivery only**. MAME's [official Linux lightgun guide](https://docs.mamedev.org/advanced/linux-lightguns.html) documents X11 lightgun/mouse configuration, not direct Wii Remote IR protocol; an IR-to-pointer translation layer would be required. RetroArch's `os/gekko/rvl/wiimote.c` is a **console Wii** Bluetooth implementation, **not** the Linux udev backend; do not treat its protocol support as evidence about Linux gyro handling.

### 5. wiiuse and CWiid — direct Bluetooth, not existing UHID/uinput

## 7. Lab handoff / acceptance gates

The local agent must obtain whatever user-owned exact-device consent/access W5 required; **this document does not authorize grants, sudo, unbind, pairing, installing system packages, editing host policy, or opening unrelated devices**. Preserve all private raw reports/captures/IDs in local-only private material and publish only sanitized evidence. Suggested repeatable oracle vector is W5's already-authorized two changing gyro drive triples with MP mode 04/05; reference [W5 diagnosis](wii-w5-gyro-diagnosis.md) for exact axis order and conditions.

1. **Cemu / raw-protocol divergence:** for one exact-owned `057e:0306` UHID, record Cemu build/commit + `HAS_HIDAPI`, Linux permission/driver, HID enumeration, status write/response, base-EEPROM calibration read, MP identity/mode write, report selection and decoded gyro event counts. Stop at any failed transition and mark it. A Cemu UI that merely lists a joystick is **not** a MotionPlus pass.
2. **xwiishow / kernel full-interface path:** snapshot owned `/sys/bus/hid/devices/.../driver` relation, owned child `input` names and MotionPlus event FD. `xwiishow list`; `xwiishow <exact-selected-index-or-syspath>`; toggle `m` and `n`, vary rotation, record min/max and normalization behavior without raw logs. Distinguish missing parent/driver from MP FD activation and no events.

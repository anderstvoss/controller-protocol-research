# Xbox 360 Wireless Receiver

## Source-only consumer evidence

- Linux xpad binds wireless vendor USB interfaces (subclass 93, protocol 129), with interrupt IN/OUT and a separate context per interface. A second consumer services four pipes; this is not a measured retail topology or simultaneous capacity. [`rcv-x360-binding`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-binding.json), [`rcv-x360-four-slot-consumer`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-four-slot-consumer.json).
- The listener starts before a pad exists. Status bits trigger attach/detach work; input and LED objects appear only on attachment and are destroyed on loss. Reattachment creates new objects; SDL HIDAPI excludes the receiver, while Linux SDL evdev tracks each node independently. [`rcv-x360-presence`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-presence.json), [`rcv-x360-evdev-epoch`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-evdev-epoch.json), [`rcv-x360-sdl-evdev`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-sdl-evdev.json).
- Connected input identity uses PID 0x02a1; global LED allocation is not a persistent slot identity. Wireless output uses a 12-byte rumble command and per-interface USB OUT, unlike wired 8-byte output. No new conventional FF or LED callbacks exist for absent slots. [`rcv-x360-identity-led`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-identity-led.json), [`rcv-x360-output`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-output.json).
- The reviewed xpad path sees headset presence but does not create headset audio, keyboard, pointer or battery nodes. Another host implementation queries battery. Local removal does not explicitly unregister siblings, while receiver unplug destroys all bindings. [`rcv-x360-companion-battery`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-companion-battery.json), [`rcv-x360-teardown`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-teardown.json).

## Inference and unmeasured behavior

Pending output cancellation at detach is not established; a USB-level presentation would be needed to test xpad receiver binding, rather than merely reproducing evdev. [`rcv-x360-output-epoch-gap`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-output-epoch-gap.json), [`rcv-x360-usb-provider`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-usb-provider.json). Retail descriptors, simultaneous slots, output actuation, pairing, fault recovery and live SDL selection remain unknown. [`rcv-x360-physical-unknown`](https://github.com/anderstvoss/controller-protocol-research/blob/eb7887bf1aacc1b0baf6f5e973cac2ee41090c4e/records/claim/rcv-x360-physical-unknown.json).

# Steam Controller 2026 wired: firmware lizard, kernel gamepad, SDL and Steam Input modes

**Scope:** direct wired Valve `28de:1302` (Triton/IBEX); source-only interpretation of pinned host and replacement-firmware code, cross-checked against **existing**, separately authorized D9 physical findings. **No hardware, D9 host, Steam runtime or virtualgamepad implementation was operated in this lane.** Version anchors: Linux v7.3-rc1 `cee9395`; SDL3 `6defbc0`; sc26re `518fa64`; real D9 Steam Stable `1792618285`, captured on 2026-11-04. Do not merge this source-only model into the implementation as physical truth.

This report answers O1–O7. *Source evidenced* describes a concrete pinned implementation, **not** proof that retail 1302 firmware or proprietary Steam follows it. *Physically observed* is used **only** when explicitly referencing already-published corpus #82/#101/D9 evidence. *Inferred* requires the D9 observations below. *Unknown* has no source-established value. GPL source is paraphrased and linked by file:line; no code excerpt is redistributed.

## Deciding component: a *product* state, not one three-way switch

The three commonly named “modes” live in **different state machines**. Report `0x42` vendor-native input is not exclusively a “gamepad firmware mode” in the same sense as the kernel's `gamepad_mode` Boolean: in historical Puck windows `0x40`/`0x41` lizard and native `0x42` **coexisted** (`sc2-july-puck-lizard-native-coexistence`). No equivalent simultaneous live-host trace is asserted here for all wired 1302 revisions.

```text
PHYSICAL 1302 / UHID report source
  USB HID descriptor: mouse collection  -> input ID 0x40 (5-byte body)
                      keyboard collection -> input ID 0x41 (8-byte body)
                      vendor collection   -> input ID 0x42 (53-byte body) ...
  Firmware lizard mapping enabled?  [stock power-on and expiry UNKNOWN]
    yes -> firmware may emit 0x40/0x41; native 0x42 may continue
    no  -> 0x40/0x41 stop or release; native 0x42 can continue
       ^ feature1 0x87 key9, 0x81, 0x85, 0x8e, key71 watchdog policy

LINUX hid-steam (IBEX, separate host state)
  physical HID input collections -> HID core mouse/keyboard path (if mapped)
  native 0x42/0x45 -> layered consumer:
    if client_opened == 0 -> kernel synthetic gamepad + motion nodes PRESENT
      if lizard_mode(module) && !gamepad_mode -> events suppressed, nodes persist
      otherwise                            -> kernel gamepad/motion events
      Menu hold (nominal 450 ms) toggles gamepad_mode + sends feature controls
    if client_opened > 0 -> raw frames forwarded to client_hdev hidraw
      native kernel synthetic gamepad/motion nodes UNREGISTER asynchronously
  closing final raw client -> native kernel nodes RE-REGISTER if still connected
    (kernel registration separately applies module lizard policy)

SDL3 HIDAPI, if enabled and active
  opens raw client -> parses 0x42 etc as SDL gamepad
  sends feature1 0x87 key9=0 initially and about every 3 s
  sensor opt-in -> feature1 0x87 key48, no explicit lizard restore at close
  SDL Linux evdev backend skips device if higher-priority HIDAPI driver owns it

STEAM CLIENT / STEAM INPUT (proprietary, partly unknown)
  may open hidraw -> same kernel raw-client handoff as above
  independently applies Steam layouts and may synthesize:
     gamepad events -> Valve Steam Virtual Gamepad 28de:11ff (Linux prior art)
     mouse/keyboard -> XTest or uinput events; not necessarily named input nodes
  game, Big Picture, desktop layout and per-game Steam Input setting -> actual
  routing/creation/removal/physical handback: NOT source-proven for Stable 1792618285
```

“Input emitted” and “node exists” must not be conflated. An evdev node can exist but remain *silent* because the kernel code gates its events. Conversely SDL creates an **application-level controller** without requiring a persistent evdev device named “SDL controller.” Steam's virtual pointer events need not create a new named keyboard/mouse node. HIDRAW open indicates access, not Steam recognition.

## O1. Firmware lizard mode

### Collections and reports

The owner-acquired 372-byte wired descriptor declares top-level **Generic Desktop Mouse** `0001:0002`, **Generic Desktop Keyboard** `0001:0006`, and **vendor** `ff00:0001` applications in a **single USB HID interface**. Lizard mouse is **input `0x40`, 5 body / 6 wire bytes**; keyboard **`0x41`, 8 body / 9 wire bytes**; native `0x42` is 53 body / 54 wire bytes. These are physical *declarations*, not proof every mode sends each report. See [physical descriptor lines 32–58](steam-s3-physical-descriptor.md#declared-reports), `steam-s3-1302-report-shapes`, and replacement implementation [sc26re `lizard.c:19–29,456–530`](https://github.com/mwdmwd/sc26re/blob/518fa645067f1dd6012f910a4575e487eccc9a5c/app/src/lizard.c#L19-L29).

The Linux driver describes firmware lizard input independently of its decoded gamepad [`hid-steam.c:1–29`](https://github.com/torvalds/linux/blob/cee9395acd8043be0644b25c34bfa86623f2b935/drivers/hid/hid-steam.c#L1-L29). Its physical-device start keeps default HID input while withholding the *physical* hidraw node; its layered `client_hdev` supplies hidraw for raw users [K:1706–1759,1782–1831](https://github.com/torvalds/linux/blob/cee9395acd8043be0644b25c34bfa86623f2b935/drivers/hid/hid-steam.c#L1706-L1759). Thus physical keyboard/mouse input is a **separate potential HIDINPUT surface** from kernel-created `Steam Controller` gamepad and `Steam Controller Motion Sensors` devices. Their exact actual D9 count, names and event routing still require inspection.

The OpenPuck **receiver** chooses **7 seconds** to fall back when Steam writes stop [OpenPuck:187–220](https://github.com/safijari/openpuck/blob/29f4d1e8b85c0a7c19e0c8b977a1a56a2c42ea6d/OpenPuck/puck_hid.cpp#L187-L220). Replacement sc26re chooses **10 seconds** and restores mapped defaults when its timer fires [sc26re:19–30,308–395](https://github.com/mwdmwd/sc26re/blob/518fa645067f1dd6012f910a4575e487eccc9a5c/app/src/lizard.c#L308-L395). **Stock firmware expiry is unknown.** USB detach, reboot, Steam exit and keyboard/mouse report idling are distinct events; no public source resolves whether retail lizard state persists across connection without reset. sc26re explicitly resets runtime registry at initialization and persists a limited haptics subtree [registry:232–259](https://github.com/mwdmwd/sc26re/blob/518fa645067f1dd6012f910a4575e487eccc9a5c/app/src/ibex_settings_registry.c#L232-L259), **not a guarantee for Valve firmware**.

## O3. SDL HIDAPI Triton and duplication

The Triton driver registers the `SDL_JOYSTICK_HIDAPI_STEAM` hint and uses that value if provided; otherwise it uses the general `SDL_JOYSTICK_HIDAPI` hint / compiled default [SDL Triton:413–426](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/hidapi/SDL_hidapi_steam_triton.c#L413-L426). The public header describes legacy **Bluetooth Steam Controller** HIDAPI as disabled by default [SDL hints:1899–1915](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/include/SDL3/SDL_hints.h#L1899-L1915); this text does **not** override the direct Triton driver's actual fallback rule. Direct `1302` is selected by VID/PID without interface-number test (Puck receiver needs 2–5) [SDL:429–471](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/hidapi/SDL_hidapi_steam_triton.c#L429-L471). SDL's active update sends key9=0 on first opportunity and about every 3 s; IMU key48 is separately set on explicit sensor enable; it sends no lizard-restore command on close [SDL:485–505,653–682](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/hidapi/SDL_hidapi_steam_triton.c#L485-L505).

**Two independent duplicate-avoidance mechanisms:** (1) SDL Linux evdev backend normally skips a device already claimed by a higher-priority SDL driver such as HIDAPI, matching VID/PID [SDL Linux:337–348](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/linux/SDL_sysjoystick.c#L337-L348), [SDL joystick:925–946](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/SDL_joystick.c#L925-L946); (2) Linux `hid-steam` raw open independently unregisters its synthetic gamepad/sensor nodes. These avoid **one class** of duplicate 1302 devices, not all duplicates with Steam's translated gamepad.

The **Steam Virtual Gamepad** on Linux is recognized by SDL as Valve **`28de:11ff`** [SDL joystick:3507–3513](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/SDL_joystick.c#L3507-L3513) and the Linux enumerator has special ordered-slot handling [SDL Linux:867–928](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/linux/SDL_sysjoystick.c#L867-L928). **Crucial detail:** SDL's gamepad layer **ignores `11ff` by default**, unless `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD` is true [SDL gamepad:3309–3323](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/SDL_gamepad.c#L3309-L3323). Generic `SDL_GAMECONTROLLER_IGNORE_DEVICES_EXCEPT` and `SDL_GAMECONTROLLER_IGNORE_DEVICES` lists then control allow/deny for other IDs, with allowlist priority when populated [SDL gamepad:161–171,3325–3335](https://github.com/libsdl-org/SDL/blob/6defbc0129b5ba90bab3f6c67bbc1e9329e24ff1/src/joystick/SDL_gamepad.c#L3325-L3335). A comment in InputPlumber reports Steam launches games with an ignore list intended to leave Steam virtual pads visible [InputPlumber `src/input/manager.rs`](https://github.com/ShadowBlip/InputPlumber/blob/117cb04e949f842397b96178bcc0d7fc7ba23acf/src/input/manager.rs), but actual environment and `ALLOW_STEAM_VIRTUAL_GAMEPAD` state in a 2026-launched SDL title remain **unmeasured**. Do not equate Steam Input opt-in with a confirmed environment string or assume `IGNORE_DEVICES_EXCEPT` alone overrides the `11ff` special case.

## O4. Steam client behavior: public evidence and unknown transitions

Public **Valve-authored** sources describe Steam Input as a translation layer between input devices and configured game layouts, supporting gamepad emulation, mouse/keyboard emulation and API integration; on Linux, emulated gamepad output is delivered through a Linux driver. The docs are **mutable public guidance**, not a pinned copy of private client code: [Steam Input Gamepad Emulation Best Practices](https://partner.steamgames.com/doc/features/steam_controller/steam_input_gamepad_emulation_bestpractices) and [Getting Started for Developers](https://partner.steamgames.com/doc/features/steam_controller/getting_started_for_devs). Neither documents an exact current wired 1302 state machine, 2026 per-game “off” handling, or Big Picture timing.

**Pinned Proton/Wine routing model (stronger than a generic guess):** [ValveSoftware/Proton `docs/CONTROLLERS.md:5–15,30–87,101–107`](https://github.com/ValveSoftware/Proton/blob/bc896217ffcd67f892f952b010f898fe7bd0f0a1/docs/CONTROLLERS.md#L101-L107) describes native Windows game input through RawInput, HID, DirectInput, XInput and SDL2/winebus.sys. It states that when Steam maps a controller, a translated **virtual Steam Controller** is exposed to the game as **XInput**, **alongside** the other access APIs; when not mapped, a game can receive the real controller through APIs it supports. This is explicit published **Proton integration design evidence** for possible native+virtual duplication. It is **not** direct proof that current Stable 1792618285 treats wired `1302` exactly the same way in every Steam Input ON/OFF setting, or that a native Linux SDL game sees the same XInput device.

Concrete **source-backed** observations:
- Kernel's own public documentation says the Steam client can consume hidraw and synthesize events through **XTest/uinput** [K:15–29](https://github.com/torvalds/linux/blob/cee9395acd8043be0644b25c34bfa86623f2b935/drivers/hid/hid-steam.c#L15-L29). This is a generic source claim, not proof which output transport Stable 1792618285 chooses for each layout.
- Valve's [`60-steam-input.rules:1–17`](https://github.com/ValveSoftware/steam-devices/blob/22ec85e5ff5ea2e15c56d71a41bcbef46356cd60/60-steam-input.rules#L1-L17) grants conditional `uaccess` to input/hidraw nodes and `uinput` (see `steam-parity-udev-valve-raw-grants`, `steam-parity-udev-uinput-wakeup`); permissions imply capability, **not** proof of creation.
- SDL recognizes virtual Steam pad `28de:11ff` and treats it specially; HHD overlay also excludes that VID/PID when iterating its own controller list [HHD `controllers.py`](https://github.com/hhd-dev/hhd/blob/4184f03b8df01e471a0cdbefc3a1297244bbac27/src/hhd/plugins/overlay/controllers.py). Code does not establish **when** Steam creates its pad.
- Source-only InputPlumber note on Steam's per-game ignore environment is secondary testimony; Proton/Wine layers can alter what a Windows title sees and have no pinned 1302 claim/handback implementation established in this survey. Do not infer Linux evdev from XInput exposure in Proton.
- **Already-published physical D9 S3**: Stable Steam opened and listed the real controller, while 55 `0x87` SET writes succeeded (including key9=0 and key50=900) and mapping commands `0x81`, `0x85`, `0x8e` appeared; the kernel's initialization is interleaved [D9 feature doc lines 10–18,50–111](steam-d9-detection-physical-2026-11-04.md). **Who issued each individual SET is not known**; transport completion does not prove lizard stopped emitting or key persistence. No authoritative Steam client source discloses its claim/restore sequence.
- **Unknown:** exact Steam client desktop/Big Picture/in-game ownership transitions, whether Steam leaves hardware accessible when Steam Input is off for one game, timing and existence of virtual keyboard/mouse **named nodes**, whether translated gamepad `11ff` persists during desktop layouts, and whether a Steam-managed 1302 and independently opened SDL HIDAPI 1302 both feed one game.

Per-game Steam Input **on** is evidence that Steam may translate according to that game's config, not proof a virtual `11ff` is *always* created, or that independent raw access disappears. Per-game Steam Input **off** does not establish Steam closes hidraw or that a non-SDL game receives raw physical input. Big Picture vs desktop should be treated as a user-layout/UI context, **not** a reliably different USB mode without capture. Steam virtual “mouse/keyboard” may be XTest-synthesized events with **no separately named evdev node**.

### Why duplicate input is possible but not guaranteed

When an SDL game is under Steam Input, the game might see the Steam virtual `11ff` plus a native HIDAPI device if its filters allow both; or it might see only `11ff`; or only the native controller if Steam Input is disabled. A separate kernel evdev gamepad and native SDL HIDAPI instance are *less likely concurrently* with `hid-steam` bound because of the raw-client unregister and SDL driver priority. The actual outcome depends on app hints, path ownership, per-game Steam translation, and asynchronous teardown—not a single fixed firmware mode.

## O7. Owner-only D9 observation checklist (read-only first, no root except approved usbmon)

Carry out with **the real retail controller**, one reader context at a time, on the owner's Linux host. All outputs below may include identifying device paths/names; they stay **private**. Publish only sanitized counts/node existence/relative timing, no captures, serials, MACs, per-host paths, device identifiers beyond model `28de:1302`, account data or wall-clock timestamps. Existing [physical plan](steam-physical-capture-plan.md) still governs safety. **No command here sends feature `0x90` or `0x9f`, enables firmware updates, rebinds a driver or changes kernel mode**.

### A. Repeat this unprivileged inventory at each state boundary

```sh
# No sudo. Keep stdout private; scrub paths, unique names and serials.
uname -r
lsusb -d 28de:1302
cat /sys/module/hid_steam/parameters/lizard_mode 2>/dev/null || true
grep -E '^(N: Name|I: Bus|H: Handlers|B: EV|B: PROP)' /proc/bus/input/devices
libinput list-devices                  # optional if installed
udevadm info --query=property --name=/dev/input/eventN   # selected N only
evtest /dev/input/eventN              # selected controller gamepad OR sensor; Ctrl-C
```

Record for each transition: event-node count and category (lizard mouse, keyboard, native gamepad, motion, `11ff` virtual pad), whether each **emits** on one reproducible control movement, `hidraw` presence and ordinary-user access, and whether Steam/SDL holds a handle (only if identifiable). `/proc/bus/input/devices` can advertise devices that do not currently emit. A `udevadm` path is a private host locator—never paste it into GitHub. If `libinput` or `evtest` is missing or permission denied, record blocked; do not change ACLs or use sudo merely to make an observation succeed. A sensor node has `INPUT_PROP_ACCELEROMETER`; use read-only input/udev classification.

### B. Test transitions, using separate neutral baselines

1. **Power / attach with no user application:** close SDL, Steam and any controller reader; start the input inventory before manual plug and after the wired `1302` appears. Try right-pad pointer movement, clicks and mapped keys, then neutral. **Caveat:** an active `hid-steam` kernel is already host software and may send `0x85/0x8e` during probe; this is *not* a firmware-alone boot experiment. A true unbound/older-kernel comparison would be a separately approved root/boot study, not this checklist.
2. **`hid-steam` only:** verify binding, native gamepad and sensor nodes, test a small button and control; distinguish silent **native** gamepad from active lizard mouse. Read module `lizard_mode`; do **not** edit it. Observe `evtest` open/close: on wired 1302, opening the sensor node should **not** itself cause a kernel IMU key48 write [K:1249–1271](https://github.com/torvalds/linux/blob/cee9395acd8043be0644b25c34bfa86623f2b935/drivers/hid/hid-steam.c#L1249-L1271).
3. **Menu hold:** with Steam/SDL closed, do a brief **~200 ms** Menu tap then a separate **~650 ms** hold, release fully and neutral between them; inspect native input emissions and lizard pointer. The source threshold is nominal 450 ms, not 650. A second hold may toggle back. Do not use this as a stopwatch measurement.
4. **SDL HIDAPI app:** launch a separately verified SDL3 3.4.10+ `testcontroller` or known SDL game, log its actual SDL library/version, hint values `SDL_JOYSTICK_HIDAPI`, `SDL_JOYSTICK_HIDAPI_STEAM`, device name/VID/PID and number of SDL gamepads. Inventory node **before, while open and after closing**; measure whether native kernel gamepad/sensor vanish asynchronously, and whether `0x40/0x41` outputs cease. SDL close sends no explicit restore.
5. **Steam at desktop:** close SDL first; start Steam manually; inspect owner-private Steam `controller.txt`, identify the physical controller's listing, any native device loss, `11ff` virtual pad presence and desktop-mapping mouse/keyboard events. Do not assume named virtual mouse/keyboard nodes. Inventory with no game running.
6. **Big Picture:** enter Big Picture while Steam remains running and **do not** start a game; repeat node/event inventory and compare with desktop, including pointer/keyboard behavior and which device emits.
7. **One SDL game with Steam Input ON, then OFF:** with same game/controller and neutral sequence, compare game-visible controller count and input mapping, physical HIDAPI vs kernel evdev, `11ff` appearance, per-game layout and duplicates. For the game process, privately inspect its environment only with operator permission: `SDL_GAMECONTROLLER_ALLOW_STEAM_VIRTUAL_GAMEPAD`, `SDL_GAMECONTROLLER_IGNORE_DEVICES`, `SDL_GAMECONTROLLER_IGNORE_DEVICES_EXCEPT`, SDL HIDAPI hints. Do **not** publish environment dumps or other variables. Repeat launch cleanly between ON/OFF; Steam Input toggles are game configuration, not USB device identity.
8. **Steam closes normally:** exit Big Picture/game then fully quit Steam; check final hidraw open count as feasible, native gamepad/sensor **re-registration**, lizard pointer return, and whether `11ff` and synthetic input cease. A Steam window disappearing does not prove its background client has relinquished raw HID.
9. **Timed restore/watchdog:** only after confirming Steam and SDL are fully closed and no other host sends key9; with optional **passive** physical usbmon capture, mark relative times 0, 3, 5, 7, 10, 15, 20 s and test one safe pointer movement/neutral at each. If kernel re-registers and sends `0x85/0x8e`, the result is **kernel restore, not hardware watchdog**. To isolate true stock expiry would require a separately authorized, controlled method to keep the raw connection open but stop lizard-refresh commands—**do not inject features or modify driver state** in this default checklist.

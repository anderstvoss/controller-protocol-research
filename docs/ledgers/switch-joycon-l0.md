# Switch 1 Joy-Con L/R — L0 source-only device ledger

**Joy-Con research, prep for virtualgamepad #297.** This ledger is source-only. No retail Joy-Con, Bluetooth connection, Linux host, USB Charging Grip or virtualgamepad build was tested. The Joy-Con registry and four seed consumer claims were merged from corpus PR #92. This lane is based on that merged groundwork.

## Evidence and shared Nintendo lineage

The common report prefix, subcommand framing and acknowledgments, SPI read envelope and rumble word encoding are already described in `swpro-l0-device-report30-full`, `swpro-l0-device-subcmd-ack-byte`, `swpro-l0-device-info02-fields`, `swpro-l0-device-factory-spi-map`, `swpro-l0-device-user-spi-magic` and `swpro-l0-device-rumble-word-tables`. They are *cross-controller leads*, not independent Joy-Con physical captures. Joy-Con-specific behavior below is based on pinned community notes, Linux `hid-nintendo` and SDL3 code, referenced through the existing corpus source records; code is paraphrased, not redistributed.

| ID | Joy-Con-specific answer | Evidence / limit |
| --- | --- | --- |
| A1 | Device-info subcommand `0x02` uses two firmware bytes at reply-data 0–1, type byte 2 (`0x01` L, `0x02` R), reserved/uncertain byte 3, six-byte MAC at 4–9 and a colour-presence indicator at 11. The Bluetooth HID product name **as emitted by retail firmware is No evidence**; SDL sets its own normalized display names `Nintendo Switch Joy-Con (L)` and `Nintendo Switch Joy-Con (R)`. | `swpro-l0-device-info02-fields`, `joycon-linux-hid-nintendo` 315–324/2495–2551, `joycon-sdl-switch` 1369–1445. Firmware values, identifier bytes and the meaning of byte 10 are not physically verified. |
| A2 | Simple input `0x3F`: button bytes 1–2, hat at 3 and Joy-Con filler at 4–11 in community notes. Full `0x30`: report ID 0, timer 1, battery/connection 2, right buttons 3, common buttons 4, left buttons 5, packed left stick 6–8, packed right stick 9–11, vibration feedback 12, three IMU frames 13–48. D-pad and L/ZL/SL/SR occupy left bits; A/B/X/Y and R/ZR/SL/SR right bits. Each stick channel uses 12-bit horizontal and vertical values. **No evidence** for required raw value of the unused opposite stick in a single half; do not assume zeros or neutral bytes. | `swpro-l0-device-report30-full`, `swpro-dekunukem-bluetooth-hid-notes`, `joycon-linux-hid-nintendo` 320–425/1740–1800. Simple mode is not equivalent to full IMU mode. |
| A3 | The shared subcommand envelope includes `0x02` device info, `0x03` report mode, `0x10` SPI read, `0x30` player LED, `0x40` IMU and `0x48` vibration. Joy-Con-specific implications include `0x38` home LED on R only, SL/SR inputs exposed outside the grip, and separate pairing/MCU commands in the common command set. The kernel and SDL do **not** exercise all command IDs: exact ACK/data behavior of shipment, rail state and pairing resets is **No evidence** at this pin. | `swpro-l0-device-subcmd-ack-byte`, `swpro-dekunukem-bluetooth-hid-subcommands-notes`, `joycon-linux-hid-nintendo` 55–95/2300–2380. |
| A4 | Factory stick calibration starts at `0x603d` for L and `0x6046` for R. The corresponding user-calibration magic+data pairs start at `0x8010`/`0x8012` and `0x801b`/`0x801d`. Factory IMU calibration spans `0x6020` through `0x6037`; user IMU magic/data begin at `0x8026`/`0x8028`. Body RGB and button RGB are found at `0x6050` and `0x6053` respectively; the shared map also lists grip colours. The two stick calibration word orderings are *not identical* in `hid-nintendo`. Exact body-type and serial bytes/format for each half are **No evidence** at these pinned consumer locators. | `swpro-l0-device-factory-spi-map`, `swpro-l0-device-user-spi-magic`, `joycon-linux-hid-nintendo` 100–140/1080–1215/1260–1320. | A5 | Each `0x30` report contains three consecutive accelerometer+gyro samples, each six little-endian signed 16-bit channels. Kernel normalizes right-half sensor axes by negating Y/Z of both accelerometer and gyro; X is unchanged. Coordinate convention: X toward triggers, Y to left, Z out of buttons. `0x40` enables IMU. This is a *consumer transformation*, not a retail IMU orientation capture. | `swpro-l0-device-report30-full`, `joycon-linux-hid-nintendo` 1380–1640, `swpro-dekunukem-bluetooth-hid-subcommands-notes`. |
| A6 | Output `0x01` and rumble-only `0x10` carry an 8-byte rumble area with four-byte *left* and four-byte *right* slots; this is true even when addressed to one Joy-Con. It **does not** mean a single half controls the other physical half. Actuator-specific high/low frequency encoding is shared with Pro research; the effect of the unused slot on a retail half is **No evidence**. | `swpro-l0-device-rumble-word-tables`, `swpro-dekunukem-bluetooth-hid-notes`, `joycon-sdl-switch` 440–510/1600–1700. |
| A7 | Full Bluetooth Joy-Con reports are nominally ~15 ms (~60–67 Hz) in kernel and community source, not necessarily at the Pro Bluetooth ~8 ms rate. Simple `0x3F` is described as state-change driven, without an established fixed interval. Kernel rate-gates subcommands on three consecutive input intervals in an 8–17 ms window, a Bluetooth gap >=60 ms, and later falls back to a legacy limiter after repeated exhaustion. Drift, latency and firmware/stack effects are unmeasured. | `swpro-l0-device-nominal-pro-report-period`, `joycon-linux-hid-nintendo` 840–955/1410–1510. |

## G. Independent device-emulator lineage

These projects emulate a Nintendo personality *toward a console or host*, rather than reading real retail packets. Their implementation can corroborate a consumer-facing **emulation shape**, but is not a physical measurement. Both source repositories and licences are pinned at full Git commit IDs, with one source record per inspected file. No upstream code is reproduced.

| Project / pin | Licence | Audited scope and relation to A/C | Limit / conflict |
| --- | --- | --- | --- |
| **mart1nro/joycontrol**, `18a09da1a04306534ff9e1df8a1a69c0192a3244` | GPL-3.0, pinned `joycon-g-joycontrol-license` | Public README and `controller.py` enumerate L type `0x01`, R type `0x02`, Pro type `0x03`; the Bluetooth protocol handler supports full-state input and common subcommand replies. Code contains conditional `0x31` handling. | NFC is explicitly **not implemented** at this pin. Do not copy its pending/unimplemented MCU behavior as device evidence or infer retail NFC. Combined Joy-Con pairing is noted as unresolved in protocol code. |
| **Brikwerk/nxbt**, `ec4b800ad6c55de96bb6c7f9f84b5bdc59a4c975` | MIT, pinned `joycon-g-nxbt-license` | README and controller enumeration support L/R/Pro emulation toward a Switch; protocol handler selects type bytes `0x01`/`0x02`/`0x03`, maintains per-side 12-bit stick representations, colors and device-info/subcommand support. | For the unused stick it emits three zero bytes for the opposite half. **This is emulator design, not evidence those bytes are correct on retail firmware.** It has basic MCU state/config reply cases, not a verified IR/NFC implementation. |
| **Maintained forks** | **No evidence** | No independently reviewed, current and commit-pinned fork was qualified in this study. | Do not guess maintenance state or treat a fork's inherited code as an independent protocol lineage. |

**Conflicts:** No confirmed contradiction between independent physical Joy-Con observations was located, since this study has no physical capture. `joycon-g-nxbt-unused-stick-emulator` must not override the explicit `No evidence` for real unused-side stick bytes in A2. `joycontrol` not implementing NFC does not conflict with consumer NFC implementations that read real hardware (see B lane); their roles differ. No `conflicts_with` reference is warranted for these non-conflicting scopes.

**Not run:** Bluetooth pairing, a Switch-console session, Linux UHID recognition, SDL, NFC and IR tests. Source paths and implementation specifics are pinned in the eight `joycon-g-*` source records.

## Implementer acceptance probes (proposed; not run)

1. Create L and R as separate BUS_BLUETOOTH UHID instances; log HID driver bind, device-info `0x21` replies, required startup subcommands and per-side evdev/IMU/LED outputs. Retain only sanitized data.
2. Compare `0x3f` and `0x30` neutral and single-button reports; verify non-participating stick, report lengths and sign transformations against consumer output.
3. Run bounded factory/user SPI calibration reads with explicit error fallback; independently check per-instance colours/type/identity metadata.
4. Exercise player/home LEDs, rumble and disconnection lifecycle, with no assumption that one half can physically drive the other.

**Status:** Source-derived only; physical fidelity and runtime acceptance are not established.

## Controller gaps 2: left-half source narrowing (2026-11-11)

Six new `joycon-cgap-left-*` claims attach specifically to `switch-joycon-left`: two source-described device/protocol claims (`identity`, `wire-fields`) and four kernel/SDL consumer claims (`kernel-buttons`, `kernel-stick`, `kernel-imu`, `sdl3-modes`). This is a narrowing of `joycon-a-full-report-per-side`, `joycon-a-right-imu-signs`, `joycon-hid-nintendo-bus-binding` and `joycon-sdl-hidapi-pair-combination`, not a replacement. The left kernel IMU requires no extra Y/Z sign flip, unlike right; SDL standalone sideways presentation rotates axes without altering raw HID fields. The unused right-stick bytes and physical descriptor remain unknown. All host and physical probes are proposed, **not run**.

# Wii MotionPlus: SDL zero gyro and HHD DualSense UHID comparison

**Research snapshot:** controller-protocol-research `main` `b4df2a3da3e35fdb517dd16908b0665d7c44f0a5` (W4 #33), SDL 3.2.10 `877399b2b2cf21e67554ed9046410f268ce1d1b2`, latest published SDL 3.4.18 `829a65d769d935c4852f8159e964312c0957260a` (2026-10-02), SDL `main` `8adc0f98837db84fd24f17c339e59dcf36a17156`, Linux `v6.12` (`adc218676eef25575469234709c2d87185ca223a`) and mainline `734bef548a96e8774d6eef5dfa2026c6edc4e80b`, and HHD `adbd50ff30614df886a6c76bd8855a64fde5d0b8`. This is *consumer-source analysis*, not a hardware trace or a reproduction. `evidence_role: consumer` is in claim scopes; physical compatibility is not promoted. No source code, descriptor arrays, addresses unique to a device, raw captures, or calibration payloads are reproduced.

## Executive conclusion

**Most useful next experiment: hold the Linux MotionPlus evdev node open before SDL initializes**, then observe whether the kernel maps `0xA600FE` and whether SDL caches a nonzero `m_ucMotionPlusMode`. The kernel creates the input node at discovery but only **requests MotionPlus use when that input node is opened**. SDL on Linux intentionally skips its own activation and local-mode assignment. Sensor *advertisement* means MotionPlus was *detected*, not that a mapped gyro payload will be *decoded*.

This is **not yet a root-cause finding**. W4 recorded MotionPlus-present and enabled gyro with all-zero readings for 60 seconds while raw semantic drive changed (raw 14-bit 9000/7000/8500 versus 7000/9000/7800). The concurrently observed activation/deactivation/reprobe traffic cannot be attributed uniquely to kernel, SDL and virtual provider from the aggregate log. In particular, SDL's initial extension-probe **can reset an already-active mapping** on Linux without directly restoring it.

**The universal claim “gyro requires dummy_hcd, not UHID” is false as an architecture rule.** Project EXP-0009 already reports changing SDL gyro over USB/UHID for DS4 and Switch Pro; HHD implements gyro-carrying virtual DualSense UHID including its Sony feature-report surface. Whether *this project's DualSense* works in SDL and Steam on a specified host remains an independent acceptance question. HHD's comment about Steam gyro-to-mouse shows its intended interoperability policy, not a disclosure of closed-source Steam internals.

## SDL Wii HIDAPI — verified code path

All three pinned Wii files have the **same relevant logic**: 3.2.10 [discovery](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L385-L428), [activation](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L450-L491), [open/registration](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L773-L799), [enable](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L860-L877), [decoder](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L1206-L1243), [dispatch](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L1266-L1298), and [periodic response](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L1396-L1435). The same paths are checked at [3.4.18](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/joystick/hidapi/SDL_hidapi_wii.c#L385-L468) and [main](https://github.com/libsdl-org/SDL/blob/8adc0f98837db84fd24f17c339e59dcf36a17156/src/joystick/hidapi/SDL_hidapi_wii.c#L385-L468). The latter two Wii source files are byte-identical at the cited pins (the W4 source records carry the SHA-256), though their encompassing SDL repositories differ. Newer versions were **not executed** locally.

1. `GetMotionPlusState` first asks for the mapped extension identity: an active MotionPlus suffix sets both **presence** and its **mode**; an inactive `0xA600FE` identity can establish presence while leaving mode NONE. See [385–428](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L385-L428).
2. `OpenJoystick` registers `SDL_SENSOR_GYRO` if `m_bMotionPlusPresent` for supported Wii+extension configurations, **without requiring** `m_ucMotionPlusMode != NONE`. See [773–799](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L773-L799). `SetJoystickSensorsEnabled` toggles the reporting flag, but Linux's `ActivateMotionPlusWithMode` performs neither the A600FE write nor the mode-variable assignment. See [457–468](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L457-L468) and [860–877](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L860-L877).
3. `HandleButtonData` can call gyro decoding only for non-NONE cached mode and at least six extension bytes. It drops invalid data when extension byte 5 bit 0 is set; byte 5 bit 1 must indicate a gyro rather than a downstream accessory report. `HandleMotionPlusData` additionally checks `m_bReportSensors`, combines three raw 14-bit fields, subtracts 8192, applies axis-dependent slow/fast scale and emits sensor data. [Packet checks](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L1266-L1298) / [gyro conversion](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L1206-L1243). A changing upstream semantic rotation is not evidence these conditions were met on the SDL input path.
4. `CheckMotionPlusConnection` and its periodic [response handler](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L1396-L1435) probe whether MotionPlus is *present*, and request reinitialization when that presence changed. They do **not** set a discovered *active mode* during ordinary polling. Thus present=true/mode=NONE remains mode=NONE until device initialization or another explicit assignment. [Periodic scheduling](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L430-L455), [update](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L1543-L1561).
5. **Opening SDL itself is a confound:** `HIDAPI_DriverWii_InitDevice` calls `ReadExtensionControllerType` before `OpenJoystick`. If it sees an active mapped MotionPlus, it resets the extension at `0xA400F0` and then calls `ActivateMotionPlusWithMode` to restore it. The restore is a no-op under Linux. This is why opening the evdev node first is a *candidate test*, not a guaranteed workaround. [Initial identify/reset](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L677-L709), [init order](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L735-L752), [Linux skip](https://github.com/libsdl-org/SDL/blob/877399b2b2cf21e67554ed9046410f268ce1d1b2/src/joystick/hidapi/SDL_hidapi_wii.c#L457-L468).

**Exact source-level preconditions for nonzero SDL gyro:** SDL HIDAPI must own/read the Wii hidraw device; device identification and final initialization must leave an active mapped MotionPlus ID for `GetMotionPlusState`; the SDL joystick type must register gyro; the caller must enable the sensor; the input report must contain a sufficiently long gyro-marked, valid extension payload; and at least one decoded angular component must differ from the neutral center after packing and scaling. Detecting MotionPlus alone satisfies only the *advertisement* part.

## Linux hid-wiimote — what activates it

**v6.12:** [module probe/open/close](https://github.com/torvalds/linux/blob/v6.12/drivers/hid/hid-wiimote-modules.c#L2771-L2839); [MP init/mode writes](https://github.com/torvalds/linux/blob/v6.12/drivers/hid/hid-wiimote-core.c#L467-L510); [hotplug/mapping decision](https://github.com/torvalds/linux/blob/v6.12/drivers/hid/hid-wiimote-core.c#L1095-L1192). **Mainline 734bef548a96:** [module open/close](https://github.com/torvalds/linux/blob/734bef548a96e8774d6eef5dfa2026c6edc4e80b/drivers/hid/hid-wiimote-modules.c#L2763-L2835), [mode selection](https://github.com/torvalds/linux/blob/734bef548a96e8774d6eef5dfa2026c6edc4e80b/drivers/hid/hid-wiimote-core.c#L467-L508) and [hotplug decision](https://github.com/torvalds/linux/blob/734bef548a96e8774d6eef5dfa2026c6edc4e80b/drivers/hid/hid-wiimote-core.c#L1093-L1190).

- **Discovery/probe:** kernel detection initializes extension/MotionPlus identification and registers an input node named *Nintendo Wii Remote Motion Plus*; the module probe does **not** set `WIIPROTO_FLAG_MP_USED`. Presence and active mapping are distinct.
- **Opening the evdev input device:** its `open` callback sets `MP_USED`, updates data-report selection, and schedules hotplug-state work. During hotplug reconciliation the kernel initializes the register blocks, detects attached MotionPlus and, when the captured `MP_USED` flag is true, writes `0xA600FE` mode **04** (alone), **05** (Nunchuk-like pass-through), or **07** (Classic-like pass-through). The kernel-side `A600F0`/`A600FB` initialization precedes mapping. The kernel also tracks `MP_ACTIVE` and `EXT_ACTIVE` state.
- **Closing the last input-node opener:** the `close` callback clears `MP_USED`, requests report-mode recalculation, and schedules reconciliation. No independently maintained gyro session is guaranteed after that last close.
- **Another process reading hidraw:** the kernel driver state is shared on the HID device and input-node open state is not automatically acquired by a hidraw reader. An evdev holder can therefore trigger mapping that an SDL hidraw consumer may see, **provided** the mapping survives SDL reset, the kernel remains bound, correct mapped ID is presented at SDL open and two clients do not interfere. This is a source-grounded *possibility*, not demonstrated persistence under W4 conditions.

Neither reviewed kernel pin performs a guaranteed always-on MotionPlus activation purely at probe. Their relevant input-node open and hotplug gating remains present. Do not infer actual kernel write order or which process initiated a captured register access without actor attribution.

## HHD DualSense-over-UHID — how it works

Pinned HHD uses [virtual device construction](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/virtual/dualsense/__init__.py#L67-L152), [UHID helper](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/lib/uhid.py#L193-L230), [report descriptors and input offsets](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/virtual/dualsense/const.py#L5-L30), and [feature handlers](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/virtual/dualsense/__init__.py#L195-L221).

- **Transport presentation.** It opens `/dev/uhid` and creates a Sony VID **0x054C** DualSense PID **0x0CE6** or Edge PID **0x0DF2** (Edge enabled by default), with bus **0x05 (Bluetooth, default)** or **0x03 (USB, optional)**, associated Sony/Edge device name, and a matching USB/BT HID descriptor. `uniq` and `phys` are synthesized ephemeral identities by the helper unless provided explicitly; a pairing feature report separately derives per-controller identity. The descriptor declares multiple vendor feature reports, but the handler implements only the listed supported queries. UHID bus metadata does not provide an actual radio or USB composite/audio topology. [Identity details](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/virtual/dualsense/__init__.py#L133-L152), [helper defaults](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/lib/uhid.py#L193-L220).
- **Feature reports.** HHD replies to GET_FEATURE **0x05** (static calibration model), **0x09** (pairing/identity information, individualized by controller index), and **0x20** (firmware/version metadata). It does not dynamically implement every descriptor-advertised feature ID. Bluetooth feature replies receive the specified protocol CRC; unknown queries are logged. These are protocol-emulation facts, *not* measured OEM per-device calibration. [Handler](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/virtual/dualsense/__init__.py#L195-L221) / [report definitions](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/virtual/dualsense/const.py#L1008-L1185).
- **Motion reports.** Signed 16-bit gyro X/Y/Z and acceleration fields are written into USB or Bluetooth enhanced report layouts. Sensor timestamp is a 32-bit little-endian counter formed from a nanosecond event divided by the HHD-provided nominal **333 ns/tick**, with optional synthetic ticks if unavailable. `sync_gyro` can require a gyro/accel/IMU timestamp event before transmission; HHD explicitly relates that policy to Steam gyro-to-mouse. A two-second absent-IMU fallback prevents indefinite silence. Bluetooth input reports are CRC protected. [Field offsets](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/virtual/dualsense/const.py#L69-L147) / [timestamp](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/virtual/dualsense/__init__.py#L363-L443) / [failover/transmit](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/virtual/dualsense/__init__.py#L516-L548).

### What SDL PS5 actually needs

At SDL 3.4.18 ([PS5 HIDAPI](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/joystick/hidapi/SDL_hidapi_ps5.c#L405-L470)), genuine Sony VID signals sensor-capability support. Enhanced report recognition and enhanced-mode availability control whether gyro is registered and can be enabled: [registration](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/joystick/hidapi/SDL_hidapi_ps5.c#L835-L885) / [enable](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/joystick/hidapi/SDL_hidapi_ps5.c#L1156-L1172). SDL reads Sony feature **0x09** serial and **0x20** firmware when enhanced reports are detected (the reads also affect Bluetooth enhanced-mode setup); these are not a single universal “gyro feature gate.” SDL loads **0x05** calibration upon sensor enable but [falls back](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/joystick/hidapi/SDL_hidapi_ps5.c#L591-L703) to a default raw conversion when short/invalid. Emission still depends on actual enhanced reports with gyro fields and the reporting flag: [packet decode](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/joystick/hidapi/SDL_hidapi_ps5.c#L1360-L1408). The PS5 implementation at SDL `main` `8adc0f98837db84fd24f17c339e59dcf36a17156` has the same source Git blob SHA as release 3.4.18 for this file; it was separately fetched. There was **no HHD+SDL host run** in this investigation.

**Transfer to Wii:** the general test methodology transfers (open order, feature/control transactions, correct report framing, event timestamps, actual nonzero consumer readings). Sony calibration IDs, identity/firmware GET_FEATURE responses, IMU timestamp format and enhanced report negotiation do **not** transfer to the Wii MotionPlus path, which is activated through extension registers and governed by hid-wiimote's evdev open state.

## Origin and limits of the dummy_hcd belief

Historical virtualgamepad guidance said dummy_hcd reportedly passed Steam gyro when the older UHID path failed: [archived AGENT_START_HERE](https://github.com/anderstvoss/virtualgamepad/blob/main/docs/history/alpha-1/AGENT_START_HERE.md) and [architecture plan](https://github.com/anderstvoss/virtualgamepad/blob/main/docs/history/alpha-1/VIRTUALGAMEPAD_ARCHITECTURE_REWRITE_AGENT_HANDOFF.md). A subsequent [context reassessment, lines 19–23](https://github.com/anderstvoss/virtualgamepad/blob/main/docs/history/alpha-1/CONTEXT_REASSESSMENT.md#L19-L23) corrected its proposed cause: both inspected historical/current UHID code snapshots used USB bus **0x03**, not BUS_VIRTUAL; original tested binary, raw trace and confounders were never recovered. [EXP-0007](https://github.com/anderstvoss/virtualgamepad/blob/main/docs/history/alpha-1/experiments/EXP-0007-bus-baseline-comparison.md) similarly did not observe consumer gyro. [Issue #154](https://github.com/anderstvoss/virtualgamepad/issues/154) currently tracks DualSense USB/UHID and uinput acceptance; [issue #176](https://github.com/anderstvoss/virtualgamepad/issues/176) keeps dummy_hcd experimental, not recommended, and reserves Steam consumer proof for a separate host test.

**SDL:** the general “UHID cannot carry gyro” assertion is contradicted by the project's [EXP-0009](https://github.com/anderstvoss/virtualgamepad/blob/main/docs/history/alpha-1/experiments/EXP-0009-family-sdl.md) (changing DS4 and Switch Pro sensors over USB/UHID). SDL PS5 code also admits the UHID protocol shape when its gates are met; **an exact HHD DualSense+SDL result was not executed**.

**Steam:** HHD implements a Linux UHID DualSense and its [source](https://github.com/hhd-dev/hhd/blob/adbd50ff30614df886a6c76bd8855a64fde5d0b8/src/hhd/controller/virtual/dualsense/__init__.py#L363-L367) explicitly adjusts emission for Steam gyro-to-mouse; the [HHD manual](https://github.com/hhd-dev/hhd/blob/master/readme.md) describes Steam motion setup. This strongly challenges topology necessity but is **not a closed-source Steam specification or a controlled same-host A/B comparison**. Do not substitute this for project #144/step P acceptance.

**Composite/audio:** dummy_hcd can provide actual USB parent/interface topology that a single UHID cannot. That separate motivation is unaffected by the gyro finding. No virtualgamepad source or issue has been edited.

## Ranked host experiments and decisive oracles

Use the **same recorded host/kernel/SDL tuple as W4** first; keep a fresh SDL process per arm. Do not modify global permission policy, detach physical devices, unbind drivers or change firmware without maintainer approval. Bind all captured events to the exact owned virtual HID and log their **origin, direction, timestamp and register address**, not serial/uniq values in public reports. Retain sensitive raw bytes privately.

A build change alone cannot prove packing correctness. |
| **H3** | Virtual provider's MotionPlus **activation or 14-bit packet packing** is defective. W4's zero readings should remain blocked for gyro until the chosen arm produces **nonzero, changing values** and no unexpected device loss over the fixed window. Do not count mere sensor enumeration or value-zero repetition as success.

## Source-specific uncertainty retained

The on-disk W4 experiment records are unchanged. This research introduces **eight Wii consumer source claims** and **five DualSense UHID consumer source claims**, with no hardware/physical promotions, unchanged historical unknowns, and no changes to virtualgamepad. The virtual Wii packing/activation bug is a *test hypothesis*, not a code diagnosis. Linux mapping persistence across competing clients and any actual HHD+SDL/Steam acceptance both require recorded host runs. Physical-controller reference equivalence is out of scope.

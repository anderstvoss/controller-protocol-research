# Xbox Wireless Adapter: xone receiver-client lifecycle

**Source-only consumer research.** No hardware, host, physical radio or firmware-content inspection. This brief extends existing `xbox-xone-receiver-bind` and `xbox-xone-receiver-clients` without changing them. xone is pinned at `f2aa9fe01103d7600553b505b298ff0bd47ff280`. Linux v7.3 is pinned at `c03c1a14507dfaf8b856c2608f9ac216021fc222`; SDL source revisions are named below.

## Identity, USB binding and capacity

The out-of-tree xone dongle driver matches Microsoft vendor `0x045e` and products `0x02e6`, `0x02fe`, `0x02f9`, `0x091e` through USB device matching, whereas xone's wired GIP transport uses a separate probe. This is not a claim about the adapter's full physical USB descriptor. The receiver uses USB bulk command and WLAN receive traffic plus bulk transmit; the host driver loads separately supplied firmware before receiver operation ([xone transport/dongle.c:1021-1069](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L1021-L1069), [xone transport/dongle.c:1076-1182](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L1076-L1182), [xone transport/dongle.c:1547-1583](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L1547-L1583)). No firmware itself was acquired, analyzed or redistributed.

xone declares a **16-entry software wireless-client table**, allocates its first free entry during association, and only ignores duplicates while that client is active ([xone transport/dongle.c:31-44](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L31-L44), [xone transport/dongle.c:482-559](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L482-L559)). **16 is not a measured maximum number of simultaneously connected controllers.** These entries are not the fixed four Puck protocol slots in ADR-0022 or GamepadManager player slots. Existing `xbox-xone-receiver-bind` and `xbox-xone-receiver-clients` already document binding and the basic per-client GIP adapter model.

## Association, removal and reconnection

A wireless association request, disassociation request, or receiver client-loss event causes the driver to enqueue an ADD_CLIENT or REMOVE_CLIENT work item on the receiver's ordered event queue. Invalid client entry numbers are rejected or ignored; a receiver that has not finished initialization does not process the event ([xone transport/dongle.c:632-689](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L632-L689), [xone transport/dongle.c:722-756](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L722-L756), [xone transport/dongle.c:820-944](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L820-L944)).

On ADD_CLIENT, xone selects a free entry, constructs a **new GIP adapter** and associates that entry with the receiver. If the client is already actively represented, the duplicate is ignored. On REMOVE_CLIENT, only that entry is cleared, its adapter destroyed, its occupancy reduced, and shared indicator state updated; other clients remain ([xone transport/dongle.c:482-591](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L482-L591)). This source does not show stable assignment of a particular client to the same numeric entry across detach/re-attach; a freed entry can be reused.

Receiver bind itself does **not** register an evdev gamepad for every entry. After wireless association creates a GIP adapter, GIP announce/identification leads to deferred GIP class registration. The gamepad class probe then registers a Linux input device. Destroying the per-client adapter unregisters its children and their input devices ([xone bus/bus.c:123-209](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/bus/bus.c#L123-L209), [xone bus/bus.c:211-290](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/bus/bus.c#L211-L290), [xone bus/protocol.c:1275-1299](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/bus/protocol.c#L1275-L1299), [xone driver/gamepad.c:265-311](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/driver/gamepad.c#L265-L311), [xone driver/gamepad.c:479-541](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/driver/gamepad.c#L479-L541)). Consequently a later connection creates a **new kernel input instance**, not a permanently retained evdev object. Whether a device path happens to reuse an earlier event number is not measured; do not equate a reused filename with device continuity. The driver's deferred host registration delay is implementation policy, not an established device-required deadline.

## Identity, battery, indicators and output

Per-client state and the GIP bus are instantiated under the live wireless entry. This review does not establish durable per-client serial persistence or stable association identity across reconnects. The GIP gamepad probe registers per-client input, power-supply battery and LED surfaces, while the receiver independently offers overall pairing/active-client controls and a shared indicator ([xone driver/gamepad.c:479-529](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/driver/gamepad.c#L479-L529), [xone transport/dongle.c:253-299](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L253-L299), [xone transport/dongle.c:384-479](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L384-L479)). The existing `xbox-xone-led-battery-power` claim already covers GIP gamepad LED and battery fields. No physical persistence or update cadence is established here.

Client output uses the live client's GIP adapter, which selects that client's wireless entry and either the data or audio queue behind common USB output URBs ([xone transport/dongle.c:130-251](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L130-L251)). Removing the client destroys that adapter; there is no remaining routed destination for subsequent output through it. These source paths do **not** establish what the physical device does if delivery races loss, whether a stale handle is accepted, or whether output is safely repeatable. Retain ADR-0022's policy: only `DefinitelyUnsent` stateful output is retryable; `Uncertain` is terminal for the owning presentation.

## Failure boundaries, teardown and companion surfaces

Removing a client does not destroy its siblings ([xone transport/dongle.c:561-591](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L561-L591)). Receive parsing failures are logged and normally followed by read URB resubmission; this does not prove sibling survival under every shared transport error, fairness bounds or recovery time ([xone transport/dongle.c:949-1010](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L949-L1010)). On USB unplug, xone attempts client power-off and destroys **all** live GIP adapters, work queues and URBs. On reset-resume it similarly discards previous client adapters and restarts receiver initialization ([xone transport/dongle.c:1252-1292](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L1252-L1292), [xone transport/dongle.c:1352-1367](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L1352-L1367), [xone transport/dongle.c:1486-1545](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L1486-L1545)).

The reviewed class path creates gamepad evdev input with battery/LED support; if headset identification qualifies, another GIP client can create ALSA playback/capture. No keyboard or pointer input is registered in the inspected xone receiver, gamepad and headset paths. This is a **bounded negative observation**, not a statement about unrelated system software. Existing `xbox-xone-gip-headset` covers conditional audio; xone is not an argument for default keyboard/pointer companions in Xbox or Puck packages.

## Pinned Linux and SDL consumer boundary

The annotated Linux **v7.3** tag peels to `c03c1a14507dfaf8b856c2608f9ac216021fc222`. Its `drivers/input/joystick/xpad.c` lists Xbox 360 receiver IDs but not the four xone Xbox Wireless Adapter IDs ([Linux v7.3 xpad](https://github.com/torvalds/linux/blob/c03c1a14507dfaf8b856c2608f9ac216021fc222/drivers/input/joystick/xpad.c#L105-L210), [xone USB matches](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/transport/dongle.c#L1547-L1583)). This establishes **stock xpad does not bind the adapter**. xone is an out-of-tree implementation of its GIP lifecycle; the negative comparison of xpad alone cannot prove absence of every possible other mainline interface driver. The v7.3 xpad Git blob matches existing source `xbox-series-linux-xpad`, though its recorded revision is different.

The pinned SDL Linux joystick backend monitors Linux evdev device additions/removals via udev, inotify or polling ([SDL Linux event backend](https://github.com/libsdl-org/SDL/blob/535d80badefc83c5c527ec5748f2a20d6a9310fe/src/joystick/linux/SDL_sysjoystick.c#L383-L610)). Separately, the reviewed SDL Xbox One HIDAPI driver is a per-device path without xone wireless association and teardown handling ([SDL Xbox One HIDAPI](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/hidapi/SDL_hidapi_xboxone.c#L364-L396)). Therefore per-client evdev nodes are the supported SDL consumer route *in source*, not evidence of a particular SDL-selected backend, connected hardware or physical gamepad behavior.

## Realization decision against ADR-0022

**uinput:** suitable only for reduced playable post-driver per-client evdev devices; it cannot bind xone's USB receiver driver or provide shared GIP association. **UHID:** a HID personality cannot satisfy the xone driver USB device-ID match by itself. **`dummy_hcd` or USB/IP:** plausible USB-level transport primitives, but not evidence of a working compatible virtual wireless adapter, full receiver protocol, radio pairing, or safe output delivery. Do **not** synthesize or falsely advertise GIP.

Retain ADR-0022's receiver-owned lifetime, typed independent slots, slot-local output, sibling-preserving removal and whole-receiver terminal cleanup. Treat xone's **dynamic association entry allocator** as an informative *different* consumer topology; it neither requires a change to the Puck's four-slot limit nor makes protocol slot IDs equivalent to app player slots.

## Proposed acceptance tests — NOT RUN

1. Record redacted receiver and evdev enumeration before/after one and multiple associations with pinned driver and host revisions; confirm the delayed GIP-to-gamepad registration sequence.
2. Detach, reattach and reorder clients while siblings remain active; distinguish kernel input instance identity from reusable evdev path numbering without recording private identifiers.
3. Inject client-local output, loss during output, shared receiver error, USB unplug and reset-resume; classify definitely-unsent versus uncertain writes and reject stale replay.
4. Probe SDL per-client hotplug, gamepad capability and optional headset audio; check the bounded absence of keyboard/pointer companion creation.
5. Measure physical simultaneous client limit and fairness; do not infer these from the 16-entry allocation.

**Evidence ceiling:** no host/hardware run, real wireless frame or firmware inspection, physical capacity, output actuation, per-slot persistent identity, evdev numbering observation, SDL acceptance or virtual USB realization. Existing virtualgamepad #165 and #160 track the relevant work; no additional issue is proposed.

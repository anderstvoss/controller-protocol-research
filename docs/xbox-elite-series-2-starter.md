## Primary pinned-source findings

### Wired Linux xpad, not a fake USB HID or GIP device

At Linux commit `4056b3c9d3c92ea45955641dbafeb9b960e146ef`, [`drivers/input/joystick/xpad.c`](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/input/joystick/xpad.c#L127-L134) marks Elite Series 2 vendor `0x045e` / product `0x0b00` as an Xbox One-path controller with `MAP_PADDLES`. The same file [advertises four distinct grip keys](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/input/joystick/xpad.c#L1973-L2005) on top of the ordinary Xbox controls, sticks, triggers and hat axes. Pinned xpad advertises no `ABS_PROFILE` for this model: that capability requires a different mapping flag. This is a **post-driver** evdev shape, not the USB protocol.

[Packet-type selection](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/input/joystick/xpad.c#L2169-L2195) uses USB `bcdDevice` thresholds `0x0500` and `0x050b` for old, early 5.x and split-packet layouts. The [input decoder](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/input/joystick/xpad.c#L1066-L1083) reads later paddle data from a separate command report; [earlier branches](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/input/joystick/xpad.c#L1165-L1209) use the main report. In those implementations a custom profile/mapping can suppress independent grip events. The xpad input capability being present is weaker evidence than an actual input event. The driver sends model-specific initialization for extra data; it does not authorize emulating GIP from uinput. Source record reused: `xbox-series-linux-xpad` (kernel GPL source, paraphrased only).

### Bluetooth kernel and optional xpadneo

At the same kernel commit, [`hid-ids.h`](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/hid/hid-ids.h#L1056-L1060) assigns model 1797 to products `0x0b05` and `0x0b22`, and [`hid-microsoft.c`](https://github.com/torvalds/linux/blob/4056b3c9d3c92ea45955641dbafeb9b960e146ef/drivers/hid/hid-microsoft.c#L427-L435) matches both on the Bluetooth HID bus. This is not evidence that a specific host attached that driver. Optional xpadneo at `56b538d951300bf804f6631738603c5eb14c04f0` [matches those same products](https://github.com/atar-axis/xpadneo/blob/56b538d951300bf804f6631738603c5eb14c04f0/hid-xpadneo/src/xpadneo/core.c#L40-L59) and [exposes grip events subject to its profile policy](https://github.com/atar-axis/xpadneo/blob/56b538d951300bf804f6631738603c5eb14c04f0/hid-xpadneo/src/xpadneo/events.c#L170-L192); `ABS_PROFILE` is an xpadneo-specific consumer surface. Descriptor changes, auxiliary nodes and HID output are conditional and must not be assumed for the stock kernel. xpadneo kernel driver code is GPL-2.0-only; descriptions here are independently paraphrased, without code excerpts. Reused source records: `xbox-cgap-kernel-hid-ids`, `xbox-cgap-kernel-hid-microsoft`, `xbox-cgap-kernel-hid-generic`, `xbox-cgap-xpadneo-core`, `xbox-cgap-xpadneo-events`, `xbox-cgap-xpadneo-device`, `xbox-cgap-xpadneo-header`.

### SDL selection, state and mappings

At SDL commit `d4557c1511c721485dc4960f7149730afc9a73a0`, [Xbox One HIDAPI code](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/hidapi/SDL_hidapi_xboxone.c#L408-L468) marks recognized Elite models paddle-capable. The [wired GIP path](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/hidapi/SDL_hidapi_xboxone.c#L1122-L1207) treats Elite Series 2 main state reports with lengths 34, 46 or 47 differently; [later separate unmapped reports](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/hidapi/SDL_hidapi_xboxone.c#L980-L1041) have their own parsing branch. The [Bluetooth HID path](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/hidapi/SDL_hidapi_xboxone.c#L1278-L1375) processes 55-, 39- and 20-byte variants, while [a descriptor-driven parser can take precedence](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/hidapi/SDL_hidapi_xboxone.c#L1959-L1998). These are code branches, not validated native packet samples. When SDL judges paddles already mapped to other controls, it suppresses separate paddle events.

The [default SDL gamepad mapping](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/SDL_gamepad.c#L1329-L1340) assigns Elite paddles `paddle1:b11`, `paddle2:b13`, `paddle3:b12` and `paddle4:b14`; this maps SDL's logical slots, not a physical evdev capture. SDL's [Linux evdev backend](https://github.com/libsdl-org/SDL/blob/d4557c1511c721485dc4960f7149730afc9a73a0/src/joystick/linux/SDL_sysjoystick.c#L2739-L2795) recognizes the four `BTN_GRIP*` codes independently and may support older `BTN_TRIGGER_HAPPY5` through `BTN_TRIGGER_HAPPY8` mappings. Both new SDL source records hash these exact pinned files and use the SDL zlib licence. For shared Xbox Series SDL paths, reuse `xbox-series-sdl-xboxone`.

## Realization decision and boundaries

1. **Build `linux.uinput` first.** Use a separate Elite Series 2 canonical input model with four independently addressable paddle inputs and explicit onboard remap/profile state. Emit the Elite `xpad` evdev shape, including grip codes, only within supported semantics. Accept caller-provided identity during creation; do not claim that evdev identity changes create a GIP or Bluetooth device. Preserve standard Xbox Series as a distinct controller.
2. **Investigate `linux.uhid.bluetooth` second.** A host-local `BUS_BLUETOOTH` UHID must supply the correct firmware/version-specific Elite HID descriptor, input reports, HID output and feature/SET_REPORT responses, profile handling, binding under `hid-microsoft` and optionally xpadneo, plus deterministic SDL acceptance. The present source inspection establishes only plausibility. Radio discovery/pairing is a separate layer; no claim of over-the-air Bluetooth function.
3. **Do not fake USB GIP.** Any true wired USB/receiver realization is gated on protocol feasibility and host validation, not just a VID/PID setting or a synthetic HID descriptor. Use the existing Xbox Series transport/GIP research for shared constraints without transferring standard Series device findings to Elite.
4. **No silent degradation.** Status must distinguish playable buttons/sticks/triggers, conditional paddle delivery, profile fidelity, independent trigger motor control, feedback, battery, lifecycle and timing. Unsupported outputs and configuration are explicit restrictions.

## Proposed tests — not run

- On a hardware host, enumerate an original wired Elite Series 2 across independently recorded firmware variants and profile slots; compare xpad capabilities, grip press/release events, suppression and SDL mapping. Do not log identifying data.
- Instantiate the proposed uinput Elite target with caller-specified identity, verify per-instance creation/removal and four grip key event paths through both Linux evdev and SDL; test profile-dependent suppression without altering the Series target.
- On a Bluetooth-capable test host, distinguish `hid-microsoft`, `hid-generic` and optional xpadneo binding and compare advertised nodes, paddle mapping, `ABS_PROFILE` and SDL HIDAPI versus evdev selection.
- For a host-local `linux.uhid.bluetooth` prototype, test descriptor parsing, four grip events, SET_REPORT and feature replies, battery/rumble semantics, device removal and two-controller isolation. Test actual radio pairing separately.
- Track unsupported USB GIP, receiver, advanced outputs, profile persistence and physical fidelity as open gaps rather than scoring them as passed.

**Evidence boundary:** all claim records are source-only or inferred, with `experiments: []`. No physical reference, host run, Bluetooth pairing, proprietary firmware analysis or vendor firmware bytes were used.

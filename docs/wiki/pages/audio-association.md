# Controller HID and audio-device association

[← Wiki home](index.md) · [Transport and host layers](transports-and-consumers.md) · [DualSense audio](controllers/dualsense/outputs-and-audio.md)

> **New consumer-source survey, 2026-11-10.** ALSA, PipeWire, WirePlumber, SDL and Wine/Proton behavior below describes inspected source components. It is not a live Steam/Proton pairing or an automatically functioning virtual audio device.

## Two independent discovery chains

A DualSense HID interface exposes gamepad reports and haptic command fields. The USB sound-card interface is separately discovered via ALSA/udev, and then by PipeWire/WirePlumber. The pinned Sony ALSA UCM profile matches specific **USB audio** identities (DualSense 054c:0ce6, Edge 054c:0df2); it does not discover a sibling from a synthetic joystick name. [audio-consumer-dualsense-ucm-usb-ids](https://github.com/anderstvoss/controller-protocol-research/blob/ce6b8d3b70fd0957135eb921ef6098988f355cb1/records/claim/audio-consumer-dualsense-ucm-usb-ids.json), [audio-dualsense-alsa-ucm-roles](https://github.com/anderstvoss/controller-protocol-research/blob/ce6b8d3b70fd0957135eb921ef6098988f355cb1/records/claim/audio-dualsense-alsa-ucm-roles.json).

Systemd ALSA rules can create `snd/by-id` and `snd/by-path` symlinks from sound-card USB and topology metadata. PipeWire's ALSA enumerator exposes bus path, card, vendor/product and serial properties for the audio device; WirePlumber applies its own audio-node naming and configuration. These are useful *audio-side* identity inputs, not an automatic join with an unrelated `UHID` device. [audio-consumer-systemd-alsa-symlink-identity](https://github.com/anderstvoss/controller-protocol-research/blob/ce6b8d3b70fd0957135eb921ef6098988f355cb1/records/claim/audio-consumer-systemd-alsa-symlink-identity.json), [audio-consumer-pipewire-alsa-udev-properties](https://github.com/anderstvoss/controller-protocol-research/blob/ce6b8d3b70fd0957135eb921ef6098988f355cb1/records/claim/audio-consumer-pipewire-alsa-udev-properties.json), [audio-consumer-wireplumber-alsa-node-identity](https://github.com/anderstvoss/controller-protocol-research/blob/ce6b8d3b70fd0957135eb921ef6098988f355cb1/records/claim/audio-consumer-wireplumber-alsa-node-identity.json).

## What the current evidence does **not** establish

The inspected SDL DualSense HIDAPI code handles controller input and output but contains no ALSA/PipeWire card lookup or HID-to-audio association in that file. Similar constraints apply to the inspected DS4 HIDAPI path. Absence from these files cannot rule out a separate Steam Input, application or system-level association algorithm. [audio-consumer-sdl-dualsense-hid-no-alsa-link](https://github.com/anderstvoss/controller-protocol-research/blob/ce6b8d3b70fd0957135eb921ef6098988f355cb1/records/claim/audio-consumer-sdl-dualsense-hid-no-alsa-link.json), [audio-consumer-sdl-dualshock4-hid-no-alsa-link](https://github.com/anderstvoss/controller-protocol-research/blob/ce6b8d3b70fd0957135eb921ef6098988f355cb1/records/claim/audio-consumer-sdl-dualshock4-hid-no-alsa-link.json).

**Unknown:** whether the proprietary Steam client or Proton automatically associates independently created controller and sound nodes, especially when `UHID` has no common physical USB parent with the sidecar audio interface. No inspected evidence demonstrates that automatic association. [audio-consumer-sidecar-hid-sound-association-unknown](https://github.com/anderstvoss/controller-protocol-research/blob/ce6b8d3b70fd0957135eb921ef6098988f355cb1/records/claim/audio-consumer-sidecar-hid-sound-association-unknown.json), [audio-consumer-proton-steam-audio-association-unknown](https://github.com/anderstvoss/controller-protocol-research/blob/ce6b8d3b70fd0957135eb921ef6098988f355cb1/records/claim/audio-consumer-proton-steam-audio-association-unknown.json).

## Implementation and verification interpretation

A virtual USB composite gadget can expose both HID and audio interfaces with shared USB ancestry, whereas independent UHID plus ALSA/PipeWire sidecars cannot acquire that topology merely by choosing the same VID/PID. Explicit application-level pairing is a possible separate design, **not** demonstrated plug-and-play compatibility. Validate card discovery, playback/capture, channel routing, mute/volume, hotplug and actual application selection independently of controller enumeration. Consult [DualSense outputs](controllers/dualsense/outputs-and-audio.md) for the distinct HID effect and ALSA channel limits.

Do not infer physical speaker/grip transducer response or advertise a virtual sound card as functional from properties alone.

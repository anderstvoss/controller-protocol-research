# Switch 1 Joy-Con L/R — L0 source-only device ledger

**Joy-Con research, prep for virtualgamepad #297.** This ledger is source-only. No retail Joy-Con, Bluetooth connection, Linux host, USB Charging Grip or virtualgamepad build was tested. The underlying Joy-Con registry and four consumer claims are in pending corpus PR #92; this lane depends on that PR.

## Evidence and shared Nintendo lineage

The common report prefix, subcommand framing and acknowledgments, SPI read envelope and rumble word encoding are already described in `swpro-l0-device-report30-full`, `swpro-l0-device-subcmd-ack-byte`, `swpro-l0-device-info02-fields`, `swpro-l0-device-factory-spi-map`, `swpro-l0-device-user-spi-magic` and `swpro-l0-device-rumble-word-tables`. They are *cross-controller leads*, not independent Joy-Con physical captures. Joy-Con-specific behavior below is based on pinned community notes, Linux `hid-nintendo` and SDL3 code, referenced through the existing corpus source records; code is paraphrased, not redistributed.

| A1 | Device-info subcommand `0x02` uses two firmware bytes at reply-data 0–1, type byte 2 (`0x01` L, `0x02` R), reserved/uncertain byte 3, six-byte MAC at 4–9 and a colour-presence indicator at 11. The Bluetooth HID product name **as emitted by retail firmware is No evidence**; SDL sets its own normalized display names `Nintendo Switch Joy-Con (L)` and `Nintendo Switch Joy-Con (R)`. | `swpro-l0-device-info02-fields`, `joycon-linux-hid-nintendo` 315–324/2495–2551, `joycon-sdl-switch` 1369–1445. | A2 | Simple input `0x3F`: button bytes 1–2, hat at 3 and Joy-Con filler at 4–11 in community notes. Full `0x30`: report ID 0, timer 1, battery/connection 2, right buttons 3, common buttons 4, left buttons 5, packed left stick 6–8, packed right stick 9–11, vibration feedback 12, three IMU frames 13–48. D-pad and L/ZL/SL/SR occupy left bits; A/B/X/Y and R/ZR/SL/SR right bits. Each stick channel uses 12-bit horizontal and vertical values. **No evidence** for required raw value of the unused opposite stick in a single half; do not assume zeros or neutral bytes. | `swpro-l0-device-report30-full`, `swpro-dekunukem-bluetooth-hid-notes`, `joycon-linux-hid-nintendo` 320–425/1740–1800. | A3 | The shared subcommand envelope includes `0x02` device info, `0x03` report mode, `0x10` SPI read, `0x30` player LED, `0x40` IMU and `0x48` vibration. Joy-Con-specific implications include `0x38` home LED on R only, SL/SR inputs exposed outside the grip, and separate pairing/MCU commands in the common command set. | A4 | Factory stick calibration starts at `0x603d` for L and `0x6046` for R. The corresponding user-calibration magic+data pairs start at `0x8010`/`0x8012` and `0x801b`/`0x801d`. Factory IMU calibration spans `0x6020` through `0x6037`; user IMU magic/data begin at `0x8026`/`0x8028`. Body RGB and button RGB are found at `0x6050` and `0x6053` respectively; the shared map also lists grip colours. The two stick calibration word orderings are *not identical* in `hid-nintendo`. Exact body-type and serial bytes/format for each half are **No evidence** at these pinned consumer locators. | `swpro-l0-device-factory-spi-map`, `swpro-l0-device-user-spi-magic`, `joycon-linux-hid-nintendo` 100–140/1080–1215/1260–1320. Do not store user-instance bytes in source control. |
| A5 | Each `0x30` report contains three consecutive accelerometer+gyro samples, each six little-endian signed 16-bit channels. Kernel normalizes right-half sensor axes by negating Y/Z of both accelerometer and gyro; X is unchanged. Coordinate convention: X toward triggers, Y to left, Z out of buttons. `0x40` enables IMU. This is a *consumer transformation*, not a retail IMU orientation capture. | `swpro-l0-device-report30-full`, `joycon-linux-hid-nintendo` 1380–1640, `swpro-dekunukem-bluetooth-hid-subcommands-notes`. |
| A6 | Output `0x01` and rumble-only `0x10` carry an 8-byte rumble area with four-byte *left* and four-byte *right* slots; this is true even when addressed to one Joy-Con. It **does not** mean a single half controls the other physical half. Actuator-specific high/low frequency encoding is shared with Pro research; the effect of the unused slot on a retail half is **No evidence**. | `swpro-l0-device-rumble-word-tables`, `swpro-dekunukem-bluetooth-hid-notes`, `joycon-sdl-switch` 440–510/1600–1700. |
| A7 | Full Bluetooth Joy-Con reports are nominally ~15 ms (~60–67 Hz) in kernel and community source, not necessarily at the Pro Bluetooth ~8 ms rate. Simple `0x3F` is described as state-change driven, without an established fixed interval. Kernel rate-gates subcommands on three consecutive input intervals in an 8–17 ms window, a Bluetooth gap >=60 ms, and later falls back to a legacy limiter after repeated exhaustion. Drift, latency and firmware/stack effects are unmeasured. | `swpro-l0-device-nominal-pro-report-period`, `joycon-linux-hid-nintendo` 840–955/1410–1510. |

## G. Independent device-emulator lineage

Candidate projects for independent corroboration are `nxbt`, `joycontrol`, and maintained forks. **No evidence** from pinned files in those codebases has yet been validated in this ledger: do not count these projects as corroboration, attribute Linux or SDL implementations to them, or assume their behavior matches physical Joy-Con. They require separately hashed, commit-pinned source records and documented licences before claims are added.

## Implementer acceptance probes (proposed; not run)

1. Create L and R as separate BUS_BLUETOOTH UHID instances; log HID driver bind, device-info `0x21` replies, required startup subcommands and per-side evdev/IMU/LED outputs. Retain only sanitized data.
2. Compare `0x3f` and `0x30` neutral and single-button reports; verify non-participating stick, report lengths and sign transformations against consumer output.
3. Run bounded factory/user SPI calibration reads with explicit error fallback; independently check per-instance colours/type/identity metadata.
4. Exercise player/home LEDs, rumble and disconnection lifecycle, with no assumption that one half can physically drive the other.
